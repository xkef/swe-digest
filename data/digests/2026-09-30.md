## Top stories

### Branch Target Reuse leaks kernel memory through stale JIT branch targets on Intel, AMD, and Arm

- **Category:** Security
- **Status:** confirmed
- **Sources:** [project](https://www.vusec.net/projects/btr/)
- **Blurb:** VUSec reads kernel memory through unprivileged classic BPF, and no Intel, AMD, or Arm CPU it tested syncs the branch predictor.
- **Summary:** VUSec describes Branch Target Reuse as a class in which the branch predictor retains targets from code that has since been rewritten, so memory freed and reused by a just-in-time compiler exposes the earlier targets. The demonstrated exploit reaches kernel memory through unprivileged classic BPF, the filter layer used by Linux socket filtering, seccomp, Docker, and Chrome. VUSec states that no CPU it tested, across Intel, AMD, and Arm, keeps the branch predictor in sync with self-modified code. Two CVEs cover the upstreamed x86 mitigation, CVE-2026-64507 for an IBPB flush on BPF JIT allocation and CVE-2026-64508 for hardening against JIT spraying. The page gives no affected or fixed kernel version ranges. It is dated 2026-09-25 and records a modification on 2026-09-29 to its mitigation section, and it carries no Hacker News thread, so the only source here is the project page itself.
- **Why it matters:** Patching is the mitigation rather than configuration, and the shipped fixes sit at different layers: Linux issues an IBPB on all cores when a classic BPF program reuses a previously executed cBPF or eBPF region, Oracle randomizes JIT code-cache locations in GraalVM, which is a language runtime rather than a kernel path, and Mozilla has not shipped an IBPB mitigation, so Firefox users rely on site isolation that is not yet complete.
- **Follow-up:** Track a Mozilla IBPB mitigation, and whether JIT-bearing runtimes other than classic BPF are shown exploitable through the same class.

### Cloudflare applies to four root programs and signs an agreement to acquire a GlobalSign root

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [announcement](https://blog.cloudflare.com/cloudflare-certificate-authority/), [HN discussion](https://news.ycombinator.com/item?id=49893144)
- **Blurb:** Cloudflare applied to four root programs and signed a deal for a GlobalSign root, and will issue only to ACME Renewal Information clients.
- **Summary:** Cloudflare states it has applied to the Chrome, Apple, Microsoft, and Mozilla root programs, and has signed a definitive agreement to acquire an established root from GlobalSign so it can issue publicly trusted certificates. It states it will only issue to clients that support ACME Renewal Information under RFC 9773. No certificate has been issued yet, and the post says general availability will take a while. Cloudflare also states it plans to be one of the first certificate authorities to issue production Merkle Tree Certificates, with the first of them issued in the first quarter of 2027, and that it is targeting Chrome's Quantum-resistant Root Program.
- **Why it matters:** Renewal automation becomes a condition of getting a certificate rather than a recommendation, and Cloudflare's stated motive is that no comparable free automated issuer exists if Let's Encrypt, which it puts at about ten million certificates a day across more than 500 million sites, has a bad week.
- **Follow-up:** Track root program acceptance, the first issued certificate, whether the ACME Renewal Information requirement survives into general availability, and whether production Merkle Tree Certificates are issued in the first quarter of 2027 as stated.

## Security

### XBOW turns a 16-byte zero write in the Linux SMC-D loopback driver into root

- **Category:** Security
- **Status:** confirmed
- **Sources:** [XBOW](https://xbow.com/blog/no-time-to-pwn-cve-2026-72018), [HN discussion](https://news.ycombinator.com/item?id=49901191)
- **Blurb:** XBOW escalates a 16-byte zero write in the Linux SMC-D loopback driver to root, succeeding on 22 of 100 boots.
- **Summary:** XBOW reports driving CVE-2026-72018, a 16-byte out-of-bounds zero write in the Linux SMC-D loopback path, all the way to root. The dibs_loopback device made SMC-D code that previously ran only on IBM Z mainframes reachable on ordinary x86, and the bounds checks were never added because the port's reviewers were not modelling a malicious peer. The exploit requires CAP_NET_ADMIN and succeeded on 22 of 100 boots with all kernel mitigations disabled. XBOW states it measured the exploit on Ubuntu 24.04 with Linux 7.1.0-rc6 on x86_64, gives no affected version range, and names no fixed stable release.
- **Why it matters:** CAP_NET_ADMIN is held by container runtimes and network daemons, and the durable finding is the class rather than the CVE: any commit that makes an obscure subsystem testable without its hardware is a candidate for the same review.
- **Follow-up:** Track the fixed stable kernel versions and distribution backports, and whether other SMC-D paths exposed by dibs_loopback carry the same missing checks.

## Languages and runtimes

### JDK 27 enables Compact Object Headers by default and makes G1 the garbage collector everywhere

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [Inside Java](https://inside.java/2026/09/28/performance-update-jdk27/), [HN discussion](https://news.ycombinator.com/item?id=49890220)
- **Blurb:** JDK 27 turns on Compact Object Headers by default and makes G1 the garbage collector in small containers too.
- **Summary:** JEP 534 makes Compact Object Headers the default, shrinking every object header from 12 bytes to 8, and JEP 519 cites 22 percent lower heap usage and 8 percent lower CPU in one SPECjbb2015 configuration. JEP 523 makes G1 the default in small containers and single-processor environments that previously got Serial GC, which changes pause times, CPU use, and memory overhead there. The Object Monitor Table is also enabled by default, its opt-out flag was deprecated on introduction because the legacy implementation is to be removed, and Inside Java states that enabling it exposed a 30 percent regression in a synchronization-heavy benchmark, which JDK-8382311 then addressed by reducing the number of fast-locking spin attempts before a monitor inflates under contention.
- **Why it matters:** Three defaults change under applications that are otherwise unmodified, the header layout change can break tooling or agents that assume the legacy layout, and one of the three has a deprecated opt-out, so each default is worth measuring separately.

### Armin Ronacher publishes Deser, a Serde alternative that moves Rust deserialization state off the call stack

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [post](https://lucumr.pocoo.org/2026/9/29/deser/), [HN discussion](https://news.ycombinator.com/item?id=49901149)
- **Blurb:** Armin Ronacher's Deser moves Rust deserialization state off the call stack and reads about 10 percent slower than serde_json.
- **Summary:** The post motivates Deser with three worked failures it attributes to Serde's design rather than to bugs: an internally tagged enum breaking when any crate in the graph turns on serde_json's arbitrary_precision, flatten turning integer map keys back into strings, and deserialize_with that cannot be applied inside an Option. The stated costs are that Deser drops non-self-describing formats such as protobuf by design, reads about 10 percent slower than serde_json on average for JSON, produces worse binary bloat, and uses unsafe internally.
- **Why it matters:** The three failures are properties of Serde as shipped, so they are worth checking against an existing codebase whether or not Deser is adopted.

- **Category:** Linux/Kernel
- **Status:** confirmed
- **Sources:** [LWN](https://lwn.net/SubscriberLink/1096827/497c985112f11386/), [slides](https://anarazel.de/talks/2026-09-23-kernel-recipes-postgres-linux/linux-postgres.pdf), [HN discussion](https://news.ycombinator.com/item?id=49895521)
- **Blurb:** Andres Freund's Kernel Recipes talk names kernel behaviours costing PostgreSQL performance, including 25 percent of CPU in futex hashing.
- **Summary:** The talk and slides list specific behaviours that cost PostgreSQL throughput: futex hash lookups taking 25 percent of CPU in some cases, a throughput plateau that disappears when cpuidle is disabled because the load is not enough to keep CPUs in a high-power state, no transparent huge pages for program text now that READ_ONLY_THP_FOR_FS is being removed, vm.overcommit_memory=2 not working inside a control group, fallocate reservations causing fragmentation and journal writes, 1GB huge pages halving performance through folio-head refcount contention, and io_uring registered buffers capped at 1GB per operation.
- **Why it matters:** Most of these are properties of process-based servers on Linux rather than of PostgreSQL, so the same items apply to any such workload.

### Basecamp publishes a Rust port of Campfire proved pixel-identical to the Rails app at completion and 20 to 95 times faster

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [repository](https://github.com/basecamp/once-campfire-rust), [HN discussion](https://news.ycombinator.com/item?id=49889976)
- **Blurb:** Basecamp's Rust port of Campfire was proved pixel-identical to the Rails original across 225 screen states when it was finished.
- **Summary:** The Rails application is pinned as a git submodule and used as the oracle, and no expected output was written by hand. A Playwright harness compares 225 screen states across three engines and four viewports on server HTML, live DOM, accessibility tree, every subresource, Action Cable frames, and screenshots at zero pixel tolerance, and the harness was first required to show Rails matching itself. Full parity held when the port was finished, and the README states the port has since diverged on purpose: the latest lean gate passed 873 of 874 cells with the web app manifest allowlisted, and CSRF tags, session cookie writes, and override digests are now excluded from comparison. Each speedup is attributed and measured separately, and the largest single gain is not Rust: indexing messages by room and creation time took the messages page from 87 to 17,972 requests per second in a 236,000-message room.
- **Why it matters:** The oracle plus differential harness is the transferable part, because it makes a rewrite's equivalence claim checkable rather than asserted.
