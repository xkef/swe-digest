### GrapheneOS has built a secure paste feature that lets users take clipboard access away from apps

- **Category:** Security
- **Status:** developing
- **Sources:** [GrapheneOS post](https://grapheneos.social/@GrapheneOS/117225731764489295), [earlier GrapheneOS post](https://grapheneos.social/@GrapheneOS/117225539756835649), [HN discussion](https://news.ycombinator.com/item?id=49590512)
- **Blurb:** GrapheneOS says it has developed a secure paste feature replacing clipboard APIs, with a merge planned soon.
- **Summary:** GrapheneOS posted from its own account on 2026-09-06 that it has developed a secure paste feature replacing traditional clipboard APIs. An app without clipboard access receives pasted content only through a user-mediated action rather than by reading the clipboard API directly. The project states it plans to get the feature merged soon and names no release.
- **Why it matters:** Replacing the clipboard API with a user-mediated paste changes an app permission that Android has always granted implicitly, and it is the kind of change other hardened Android builds tend to follow.
- **Follow-up:** The merge landing, the GrapheneOS release that ships secure paste, the app compatibility fallout, and whether AOSP or other hardened builds adopt the same model.

### HN thread reports about 4,000 BTC moved out of the Liquid Federation wallet after a public range proof fix

- **Category:** Security
- **Status:** rumor
- **Sources:** [Elements commit c26d719](https://github.com/ElementsProject/elements/commit/c26d719), [HN discussion](https://news.ycombinator.com/item?id=49591672)
- **Blurb:** An unverified Hacker News thread claims about 4,000 BTC left the Liquid Federation wallet after a public range proof cache fix.
- **Summary:** The Elements commit c26d719, titled as a fix binding the range proof cache to asset and scriptpubkey, was authored by delta1. That commit is the only part of this story confirmed against a primary source. The reported theft from the Liquid Federation wallet, the sidechain pause, and the on-chain OP_RETURN negotiation could not be checked against any primary source from this run.
- **Comments:** HN commenters, including the account nullc, who states he wrote the original range proofs at Blockstream, argue the fix introduced an undelimited hash field collision worse than the cache bug it closed. The roughly 4,000 BTC figure and the sidechain pause rest on that thread alone. The submission points at a Liquid_BTC post on X that was not readable, because X is unreachable and xcancel.com serves a browser verification challenge, and mempool.space transaction pages render empty.
- **Why it matters:** If the thread is right, a security fix that shipped as an ordinary public commit introduced a worse bug than the one it closed, which is the failure mode any project that patches in the open has to plan for.
- **Follow-up:** A Blockstream or Liquid Federation statement, the amount and the sidechain status confirmed on chain, and whether a second fix lands for the collision the thread describes.

## Security

### OpenChoreo patches a cluster gateway proxy that authenticated no caller and allowed Secret reads across every connected data plane

- **Category:** Security
- **Status:** confirmed
- **Sources:** [GHSA-rh53-xvx2-j327](https://github.com/advisories/GHSA-rh53-xvx2-j327), [CVE-2026-73842](https://nvd.nist.gov/vuln/detail/CVE-2026-73842)
- **Blurb:** OpenChoreo patched a cluster gateway proxy that authenticated no caller and allowed Secret reads across data planes.
- **Summary:** The OpenChoreo advisory describes an internal cluster-gateway listener that performs no caller authentication and grants tunneled Kubernetes access to every connected data plane, including Secret reads. The client library's read-only restriction is not enforced server side. Fixed in 1.0.3, 1.1.3, and 1.2.0.
- **Why it matters:** Anyone running OpenChoreo needs 1.0.3, 1.1.3, or 1.2.0, because the internal listener grants tunneled Kubernetes access with no caller check.
- **Follow-up:** Whether the listener gains authentication rather than only network-level restriction, and any reported exploitation.

### A Python interpreter in 1024 bytes of C89 that reparses the source on every loop iteration

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [Austin Henley](https://austinhenley.com/blog/python1024.html), [HN discussion](https://news.ycombinator.com/item?id=49591876)
- **Blurb:** A 1024-byte C89 program runs a Python subset by reparsing the source text on every iteration of a loop.
- **Summary:** The write-up walks through a Python subset interpreter written in 1024 bytes of C89. It uses a recursive descent parser that executes as it parses, with no intermediate representation and no bytecode, so a loop body is reparsed on every iteration.
- **Why it matters:** It shows how far a parser that executes as it parses can go with almost no interpreter state.
