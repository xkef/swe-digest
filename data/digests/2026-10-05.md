### Denmark confirms unauthorized parties reached 8.8 million CPR records by abusing a company's lawful section 38 access

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.cpr.dk/cpr-nyt/nyhedsarkiv/2026/okt/omfattende-uautoriseret-adgang-til-borgeres-cpr-oplysninger), [ministry](https://ufm.dk/aktuelt/pressemeddelelser/2026/oktober/omfattende-uautoriseret-adgang-til-borgeres-cpr-oplysninger/), [report](https://cphpost.dk/2026-10-05/life-in-denmark/cpr-data-breach-exposes-personal-details-of-8-8-million-people-in-denmark/), [discussion](https://news.ycombinator.com/item?id=49962012)
- **Blurb:** Denmark says unauthorized outsiders abused a company's lawful section 38 CPR access, reaching 8.8 million registered persons.
- **Summary:** The CPR administration published a news item dated 2026-10-05 stating that unauthorized outsiders obtained the data by misusing a Danish company's lawful CPR access, and it links a press release of the same date from the Danish ministry for research, education and digitalisation that names the legal basis as section 38 of the CPR law, which lets a private company with a legitimate interest retrieve data only on persons it has already identified one by one, by CPR number, by birth date and name, or by name and address. The 8.8 million figure counts registered persons including living, emigrated and deceased, against a register the ministry puts at about 11 million, the activity ran through September, the CPR administration became aware of it on the evening of Friday 2026-10-02, and both primaries state that the access does not cover names and addresses of persons registered with name and address protection. Both also state that the company's access has been stopped, that the CPR administration has filed with Datatilsynet, and that the police are investigating, while the ministry release alone adds that the minister informed the Folketing's business and digitalisation committee and ordered a full security review of CPR, and that the investigation is in an initial phase with no attribution currently possible.
- **Why it matters:** Section 38 exposes a per-person lookup interface, so reaching about 8.8 million records means outsiders drove that interface at register scale through September before the administration noticed on 2026-10-02.
- **Follow-up:** Watch for who the police attribute the access to, for the company's name, and for the fields reached beyond names, addresses, and CPR numbers, which neither primary states.

### mold 3.0.0 ships the high-speed linker rewritten in Rust as a drop-in replacement for the C++ version

- **Category:** Dev tools

- **Summary:** The v3.0.0 release notes state that mold is now written in Rust and is intended as a drop-in replacement for 2.42.1, the last C++ release, with the same options, targets and link performance, verified by building all Gentoo packages with no regressions. - **Why it matters:** Anyone who builds mold from source loses the CMake path this release, because the build moves to Cargo and requires a Rust toolchain of 1.95 or later.

### A mock run stretched a Go stop-the-world pause to 40ms by swapping out the collector's metadata

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://frn.sh/go-gc/), [reproduction](https://github.com/frnsimoes/go-gc-swap-cost), [discussion](https://news.ycombinator.com/item?id=49959654)
- **Blurb:** Under induced memory pressure on a Hetzner box, median Go pauses held near 51us while the worst case reached 40ms from swap.
- **Summary:** The post, dated 2026-09-13, traces a 40ms stop-the-world pause to garbage collector metadata the kernel had paged out to swap, so the collector read its own bookkeeping from disk with every P halted. The author measures this in a mock run under induced memory pressure, on a Hetzner box running kernel 6.8 with MGLRU enabled, rather than in an observed production incident, and reports a median pause of about 51us against a 40ms worst case with the metadata on NVMe. The bookkeeping lives outside the heap and is reused rather than freed, which is what lets it go cold enough for the kernel to age it out while the process stays busy, and a 2026-09-14 update measures Go 1.26 Green Tea against the same case and reports a negligible change.
- **Why it matters:** Go GC bookkeeping sits outside the heap and is reused rather than freed, so a host under memory pressure can turn a routine pause into disk latency paid with every P halted.

## Security

### Xray-core certificate pinning skipped hostname verification on two dial paths

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://github.com/XTLS/Xray-core/security/advisories/GHSA-5wf9-h793-w73c), [discussion](https://github.com/net4people/bbs/issues/672), [further discussion](https://news.ycombinator.com/item?id=49956003)
- **Blurb:** Pinning a CA hash in Xray-core skipped hostname checks, so any leaf from that CA could MITM Hysteria2 and gRPC dials.
- **Summary:** GHSA-5wf9-h793-w73c, published 2026-07-10, records that setting `pinnedPeerCertSha256` in Xray-core turns off the standard certificate verification rather than adding to it, so hostname checking was skipped whenever `ServerName` ended up empty. The advisory's title and vulnerable branch scope the machine-in-the-middle condition to a pinned well-known, non-self-signed CA certificate: when the pinned hash matches a CA rather than the presented leaf, any leaf issued under that CA satisfies the check. Pinning a leaf certificate's own hash is not in that scope, because the presented leaf is then matched directly. The advisory states that Xray-core usually derives `ServerName` from the server address, and names the two paths where it does not and so leaves neither `dNSName` nor `iPAddress` checked: the Hysteria2 dialer, and gRPC dial when the address is an IP address rather than a domain. It lists affected versions from v26.1.13 and patched versions from v26.7.11, rates the severity Low, and records no known CVE, and the net4people thread holds that the first code change addressing the flaw shipped without a security note, which was not verified against the commit and release history here.
- **Why it matters:** Pinning a shared CA's hash through `pinnedPeerCertSha256` is weaker than ordinary verification on those two dial paths, because every leaf that CA issues then passes.
