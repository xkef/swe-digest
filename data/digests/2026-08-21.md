## Top stories

### GitHub's CTO says the 7 hour 47 minute August 17 outage was a capacity failure, and reports Azure now serves 58 percent of platform load

- **Category:** Outage
- **Status:** confirmed
- **Sources:** [GitHub blog post](https://github.blog/news-insights/company-news/the-august-17-outage-and-the-work-ahead/), [GitHub status incident analysis](https://www.githubstatus.com/incidents/zkxwbgr0cnmx), [HN discussion](https://news.ycombinator.com/item?id=49378957)
- **Summary:** The company blog post states that neither August incident came from a code or configuration change and that both were capacity failures, and it puts numbers on the migration underneath. Azure serves roughly 58 percent of platform load and half of all Git operations, up from 12 percent of platform load in May, and monthly commits grew from 1.4 billion to 2.9 billion since April. GitHub's own root cause analysis on its status page names a narrower immediate cause, network saturation on Central US load balancers caused by an Istio sidecar pod reaching its concurrency limits and failing to auto scale correctly because of a misconfigured policy that watched host service limits but not sidecar limits. That analysis carries operational figures the blog post omits: peak error rates near 20 percent for web and API and near 50 percent for archive and raw content, four HAProxy nodes exhausting their flow limits, a latent retry bug in VS Code amplifying traffic roughly 10x, Copilot Token Service traffic rising from a normal 7,000 to 9,000 requests per second to 70,000 to 100,000, and scraping against codeload endpoints impeding recovery. A misconfigured autoscaling policy sits uneasily against the blog post's statement that no configuration change was involved. The named remediations are consistent retry limits, retry budgets and variable timeouts across service-to-service calls to stop retry storms, and a review of lower-priority CPU and memory alerts for components that fail under sudden spikes.
- **Why it matters:** The remediations are ones any service owner can apply without GitHub's scale, and the disclosed migration numbers change how much of the platform a single cloud now carries.
- **Follow-up:** The promised root cause analysis is published, so the open question narrows to whether the retry budget and variable timeout work is reported as landed.

### Mailpit reintroduced the cross-site WebSocket hijack it patched in January, because the origin gate reads the raw URI while the router reads the decoded path

- **Category:** Security
- **Status:** confirmed
- **Sources:** [GitHub advisory GHSA-8r62-w5wh-fc5m](https://github.com/advisories/GHSA-8r62-w5wh-fc5m), [Mailpit 1.30.6 release](https://github.com/axllent/mailpit/releases/tag/v1.30.6)
- **Summary:** The advisory publishes the affected range as Mailpit 1.29.0 through 1.30.5, patched in 1.30.6. The origin check is applied against the raw request URI while the router dispatches on the decoded path, so a percent-encoded path reaches the WebSocket endpoint without the origin check matching it, and a page on any other origin can open the socket in the visitor's browser and receive messages as they arrive. The advisory tracks this as CVE-2026-67448 and records it as a regression of CVE-2026-22689, fixed in commit 6f1f4f3 on 2026-01-10 and shipped in 1.28.2, then reintroduced in commit a63bcd9 on 2026-01-31 and first released in 1.29.0. The attack requires Mailpit running in its default configuration, because the advisory states that with `--ui-auth-file` set the percent-encoded path returns 401 rather than a 101 upgrade.
- **Why it matters:** Mailpit holds exactly the mail a developer machine is not supposed to send, including password reset tokens, and on an affected version run without `--ui-auth-file` any page the developer visits can read it live.

### Torvalds traces repeatable Xe GPU job timeouts to a two-year-old flat CCS rounding bug that hands reserved VRAM back as usable memory

- **Category:** Linux/Kernel
- **Status:** confirmed
- **Sources:** [dri-devel message](https://lists.freedesktop.org/archives/dri-devel/2026-August/590630.html), [r/linux discussion](https://www.reddit.com/r/linux/comments/1vu7aw9/linus_torvalds_uses_ai_to_debug_an_intel_gpu/)
- **Summary:** Torvalds writes on dri-devel that repeatable job timeouts on Intel Xe hardware trace to a rounding error in the flat CCS reservation that has been in the driver for about two years. The effect is that part of the range the hardware has already taken is handed back to the allocator as usable VRAM, so any allocation placed there is silently corrupted. The linked Reddit submission title states that he used AI to debug the driver, and the message itself contains no mention of AI tooling of any kind, so that claim is not carried here.
- **Why it matters:** A driver that publishes memory it has already stolen for hardware use corrupts whatever lands there, and when that is a GPU page table the failure surfaces as an unrelated engine reset.
- **Follow-up:** Track which stable kernels take the fix.

## Infrastructure

### PgBouncer transaction mode leaks session state between clients, so one read-only transaction can make a whole pool reject writes

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [PlanetScale blog](https://planetscale.com/blog/postgres-poisoned-connection-pools), [HN discussion](https://news.ycombinator.com/item?id=49378424)
- **Summary:** In transaction mode each backend connection is reused across clients, so a `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` or `default_transaction_read_only = on` outlives the transaction that set it and every later client inherits it. The symptom is Postgres error 25006 and writes failing with `cannot execute INSERT in a read-only transaction`, which reads like a read-only cluster but is not, and the post gives the distinguishing error text. The fix is `DISCARD ALL` on every pooled connection, and the prevention is routing reads to a replica instead of enforcing read-only on primary transactions. The post is vendor-authored, and the failure mode is a property of PgBouncer transaction mode that applies to any Postgres deployment behind it.
- **Why it matters:** A single client setting a session-level flag can make an entire connection pool reject writes with an error that points at the wrong cause.

### DuckDB v2.0 replaces its PostgreSQL-derived SQL parser with a PEG parser that extensions can add grammar rules to at runtime

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [DuckDB blog post](https://duckdb.org/2026/08/20/duckdb-20-peg-parser), [HN discussion](https://news.ycombinator.com/item?id=49387349)
- **Summary:** The parser front end changes while the binder and the rest of the query pipeline keep operating on the same internal AST, and DuckDB states existing queries should continue working. The concrete defect the rewrite fixed is exponential parse time on malformed input, where on the experimental parser shipped in v1.5 each additional unmatched opening parenthesis roughly doubled parse time, at 5.303 seconds for 18 and 10.640 seconds for 19, and packrat memoization brought 19 down to 0.001 seconds. The extension API shown is a preview that may change before release, and it lets an extension register grammar rules against DuckDB's own rules and reuse existing transformers.
- **Why it matters:** Extension grammar rules replace today's fallback parsers, which have to reimplement the surrounding SQL and cannot be combined with each other.
- **Follow-up:** Track the DuckDB v2.0 release and the final form of the parser extension API.

### Two Cassandra BATCH writes that tie on timestamp can leave a durable state neither batch wrote

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [theconsensus.dev post](https://theconsensus.dev/p/2026/08/16/transactions-in-cassandra.html), [HN discussion](https://news.ycombinator.com/item?id=49386877)
- **Summary:** Phil Eaton runs an accounting workload against a three-node cluster on the pre-release `cassandra-6.0` branch and reproduces the behavior by hand. Batch timestamps are client-generated and Cassandra breaks a tie per cell by keeping the greater value rather than per row, so two batches issued at the same explicit timestamp, one writing 100 and 1900 and the other writing 1800 and 200, leave 1800 and 1900 in the table, a sum of 3700 against a two-account invariant of 2000. The article also shows plain quorum updates violating the invariant on 939 of 1500 concurrent reads, and cross-partition BATCH holding atomicity but not isolation.
- **Why it matters:** This is documented last-write-wins conflict resolution rather than a defect, which is what makes it easy to miss when modelling a ledger on Cassandra.
- **Follow-up:** Track Accord, the strictly serializable cross-partition option, which arrives when Cassandra 6 is released. The article was read only to the fetcher's 20,000 character truncation, which falls before its Accord section.

### Cursor's Vicent Marti explains why distributed filesystems and object-level Git stores both failed, and what limits GitHub's Spokes replication today

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [Cursor blog post](https://cursor.com/blog/git-at-any-scale), [HN discussion](https://news.ycombinator.com/item?id=49348141)
- **Summary:** The post walks the storage designs Git hosting has used and ties each discarded one to a specific constraint. Reads inside a packfile are random walks over the object graph rather than sequential streams, which is what defeats putting repositories on a distributed filesystem. The object-level design, Shawn Pearce's JGit DHT work at Google, was discarded for a different reason, because the Git protocol requires packfiles to be sent over the network regardless of how the server stores the data, which made clone performance bad enough to abandon the design. Eventual consistency appears later in the post as a constraint on replication rather than on object storage, as the reason GitHub's Spokes keeps all replicas synchronously consistent. The post then gives the limits of Spokes and names Cursor's replacement, Continuity, which this run could not read because the fetch truncated at the start of that section.
- **Why it matters:** Each design is ruled out by a different property, packfile reads as random walks for the distributed filesystem and packfiles on the wire for the object store, so a reader can tell which constraint their own storage choice runs into.
- **Follow-up:** Read the Continuity section when the page can be fetched in full.
