## Top stories

### WeWorm: a zero-click worm that spreads through WeChat calls across iOS and Android

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://calif.io/research/weworm), [discussion](https://news.ycombinator.com/item?id=49609900)
- **Blurb:** Calif.io details WeWorm, a zero-click WeChat VoIP worm taking over accounts on iOS and Android with no user interaction.
- **Summary:** Calif.io describes a memory-corruption bug in the VoIP stack of WeChat that yields full account takeover through an incoming call, with no user interaction, on both iOS and Android. The researchers state that working with AI their team found the bug and wrote the first remote code execution exploit in about two days, that the team supplied the judgment on what to target, and that building the worm took one more week. Tencent published WeChat Android 8.0.77 and iOS 8.0.76 on 2026-08-21 mitigating the bug, and Calif.io states server-side mitigation was confirmed for all users on 2026-08-28.
- **Why it matters:** A messaging app with over a billion users had a zero-click account takeover path, and the team reports two days from bug to first remote code execution exploit working with AI, plus one further week to build the worm.
- **Follow-up:** Track any confirmation of exploitation in the wild.

### An LLM-assisted patch series speeds Linux kernel builds by 36 to 90 percent

- **Category:** Linux/Kernel
- **Status:** confirmed
- **Sources:** [primary](https://www.phoronix.com/news/AI-To-Faster-Linux-Kernel-Comp), [discussion](https://news.ycombinator.com/item?id=49619470)
- **Blurb:** An LLM-assisted patch series parallelizes single-threaded Kbuild stages for 36 to 90 percent faster kernel builds.
- **Summary:** Lorenzo Stoakes reports an all-modules build about 36 percent faster, incremental builds up to 70 percent faster and noop builds up to about 90 percent faster. The patches parallelize stages that ran single-threaded in Kbuild, kallsyms, modpost, objtool, mksysmap and the Rust build system.

### Kimi K3's full 2.8T weights run on one MacBook Pro with experts streamed from four SSDs

- **Category:** AI
- **Status:** confirmed
- **Sources:** [primary](https://github.com/argonautlabsai/deltafin), [discussion](https://news.ycombinator.com/item?id=49616257)
- **Blurb:** A deltafin fork runs Kimi K3's full 2.8T weights on one M5 Max MacBook Pro at about 1 token per second from four SSDs.
- **Summary:** The argonautlabsai fork of deltafin reports running the full 2.8 trillion parameter Kimi K3 weights on one M5 Max MacBook Pro with 128 GB by streaming experts from four external SSDs, on the engine built by the upstream gavamedia project. The fork measures about 1.00 token per second steady decode over 512 tokens and states that a 512-token prompt takes about 6.3 minutes to its first token. Its drive ladder shows one drive at about 52 percent of four-drive speed, two at about 73 percent and three at about 90 percent.
- **Why it matters:** The sublinear ladder shows the slowest of each layer's 16 reads sets the pace, so latency spread across drives matters more than aggregate bandwidth.

## Languages and runtimes

### Replacing a 16-byte Rust enum with a 64-bit tagged word made every interpreter benchmark faster

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://pointersgonewild.com/2026-08-25-replacing-a-rust-enum-with-a-64-bit-word/), [discussion](https://news.ycombinator.com/item?id=49575914)
- **Blurb:** Replacing a 16-byte Rust enum with a 64-bit tagged word cut peak RSS by up to 37 percent and sped every benchmark.
- **Summary:** Rust's alignment rules pushed a tagged enum whose largest variant needs 64 bits out to a full 128 bits. Replacing it with low-bit tagging in a single 64-bit word cut peak RSS by up to 37 percent and improved every benchmark, including the float-heavy ones the author expected to regress.
- **Why it matters:** Enum layout in Rust can silently double a value representation, and the cost shows up as memory traffic rather than as anything visible in the source.

## Apple platforms

### A 40-year-old off-by-one in XNU gives the first UNIX-domain socket a changing inode

- **Category:** Apple
- **Status:** confirmed
- **Sources:** [primary](https://yuvalino.com/how-can-you-not-be-romantic-about-unix-domain-sockets), [discussion](https://news.ycombinator.com/item?id=49617860)
- **Blurb:** A 40-year-old off-by-one in XNU gives the first UNIX-domain socket stat'd on a booted system a changing inode.
- **Summary:** XNU's uipc_sense uses unp_ino++ where it needs ++unp_ino, so the first socket stat'd on a booted system gets inode 0. The same code reads 0 as uninitialized and reassigns a new inode on the next call. The author traces the line back through XNU 123.5 and 4.3BSD-Tahoe to a 1985 change, and states it is not interesting from a security standpoint.
- **Why it matters:** Code that keys on socket inode numbers can see the identifier for one socket change between two stat calls.
