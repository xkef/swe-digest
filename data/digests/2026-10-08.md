### Atlassian patches a pre-auth file read in eight Data Center products, and a public exploit chain turns it into Jira administrator

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://github.com/advisories/GHSA-gr66-x5pq-8g2g), [research](https://labs.watchtowr.com/you-wont-hear-about-these-even-in-myths-atlassian-jira-confluence-and-more-pre-auth-arbitrary-file-read-cve-2026-21589/), [discussion](https://news.ycombinator.com/item?id=50005577)
- **Blurb:** Atlassian patched a pre-auth file read in eight Data Center products, and watchTowr chained it to Jira administrator.
- **Summary:** The GitHub advisory record GHSA-gr66-x5pq-8g2g carries the Atlassian advisory text for CVE-2026-21589, rated CVSS v4 9.3 critical under CWE-552, with the base metrics `CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N`, so attack complexity is low, there are no attack requirements, and no privileges or user interaction are needed. NVD published it on 2026-10-05. The affected list covers all versions of Bitbucket, Confluence, Jira Software, Jira Service Management, Bamboo, Crowd, Crucible and Fisheye Data Center back to releases as old as Bitbucket 4.6.0 and Confluence 5.10.0. Atlassian states that exploitation requires prior knowledge of the exact file path and that directory listing is not possible, and watchTowr published a chain that reads one documented path, `WEB-INF/classes/crowd.properties`, which stores the Crowd application password in plaintext, then uses it to add an attacker-created user to `jira-administrators`. The vendor advisory page itself was not read on this run, and the two sources disagree on one fixed version, with watchTowr listing Crowd 7.1.7 against 7.1.1 in the advisory record, so the versions above are the advisory record's.
- **Why it matters:** Atlassian states that exploitation needs prior knowledge of the exact file path and that directory listing is not possible, and the published chain needs only one documented path, `WEB-INF/classes/crowd.properties`, which stores the Crowd application password in plaintext and leads to adding an attacker-created user to `jira-administrators`.
- **Follow-up:** The fixed version for Crowd confirmed from the vendor advisory page, and any report of exploitation in the wild.

### Tensorlake npm package shipped a credential worm that wipes the home directory if the stolen token is revoked

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.stepsecurity.io/blog/tensorlake-npm-compromised-hostage-token-worm), [issue](https://github.com/tensorlakeai/tensorlake/issues/1014), [discussion](https://news.ycombinator.com/item?id=50001272)
- **Blurb:** Tensorlake npm 0.5.144 installs a service that runs `rm -rf` on the home directory when the stolen GitHub token dies.
- **Summary:** StepSecurity names tensorlake 0.5.144 as the malicious release, 0.5.143 as the pin, and tensorlakeai/tensorlake main commits e90c47b to 6386121 as the compromised range. The release was built from the project's own main branch and carries a valid npm provenance attestation, and StepSecurity found 0.5.144 still downloadable from npm when it checked. The package steals a GitHub token and installs a background service that deletes the user home directory once the token stops working, so the published remediation order is to remove `~/.config/gh-token-monitor` first and rotate credentials afterwards.
- **Why it matters:** Revoking the stolen GitHub token first triggers the background service that runs `rm -rf` on the user home directory, so the standard first step of incident response is what causes the damage, and a valid provenance attestation on a build from the project's own main branch defeats a provenance-trust policy.
- **Follow-up:** Whether 0.5.144 is removed from the registry, and what the project publishes on scope.

### Paper argues Lean verification of AI autoformalisation proves nothing about the prose proof, and that OpenAI's Navier-Stokes case shows it

- **Category:** Paper
- **Status:** confirmed
- **Sources:** [primary](https://arxiv.org/abs/2610.08144), [discussion](https://news.ycombinator.com/item?id=49994145)
- **Blurb:** A paper argues a passing Lean check says nothing about the prose proof it was translated from, citing OpenAI's release.
- **Summary:** The authors argue that a successful Lean check validates only the formal statement that was produced, not the natural-language argument it was translated from. They place that translation problem above the halting problem in the Solvability Complexity Index hierarchy. They use OpenAI's Navier-Stokes material as the worked case.
- **Why it matters:** Any pipeline that treats a passing Lean check as evidence that a model-written argument is correct depends on a faithful natural-language to formal translation that the paper argues is not decidable.

## Engineering posts

### incident.io traces a Postgres queue ceiling to MultiXact lock contention caused by per-item savepoints

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [primary](https://incident.io/blog/how-savepoints-quietly-throttled-our-postgres-queue), [reddit](https://www.reddit.com/r/programming/comments/1x02iea/how_savepoints_quietly_throttled_our_postgres/)
- **Blurb:** incident.io found per-item savepoints put a MultiXact in every locked row, capping its Postgres queue throughput.
- **Summary:** incident.io ran each item of a FOR UPDATE SKIP LOCKED batch in its own savepoint, which placed a MultiXact in every locked row. Each skipped row then cost a MultiXact lookup behind one lightweight lock, so adding workers made claim acquisition slower. Splitting the claim from the work gave a 3.5x throughput gain.
- **Why it matters:** A queue built on SKIP LOCKED can hit a ceiling that looks like database load but comes from how the claim transaction is structured.

### Push ifs up and fors down, with the algebra that says when each rewrite is legal

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [primary](https://debasishg.github.io/blog/push-ifs-up-fors-down/), [discussion](https://news.ycombinator.com/item?id=49997073)
- **Blurb:** A post gives the preconditions that make pushing conditions up and loops down a legal rewrite rather than a style rule.
- **Summary:** The post states the preconditions behind the idiom. A condition only leaves a loop when it is loop invariant. A selection moves below a join only when it touches one side. Filtering before mapping holds as filter p . map f == map f . filter (p . f) and pays only when p . f reduces to a cheap test on the input.
- **Why it matters:** The idiom usually circulates as a bare style rule, and the stated preconditions are what separate a safe rewrite from a behaviour change.
