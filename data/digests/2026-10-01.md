### Apple patched an exploited CoreGraphics bug, researchers published the PDF font path (CVE-2026-86950)

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://calif.io/research/the-great-glyph-grift), [discussion](https://news.ycombinator.com/item?id=49915669)

### Cloudflare commits to post-quantum Merkle Tree TLS certificates, first issuance targeted for Q1 2027

- **Category:** Security
- **Status:** developing
- **Sources:** [primary](https://arstechnica.com/security/2026/09/cloudflare-plans-to-issue-quantum-safe-tls-certificates/), [discussion](https://news.ycombinator.com/item?id=49908627)
- **Blurb:** Cloudflare targets Q1 2027 for its first Merkle Tree TLS certificates, holding handshake data near 40 KB, about today's size.
- **Summary:** Ars Technica reports that Cloudflare plans to issue quantum-safe TLS certificates built on the Merkle Tree Certificate design, with first issuance targeted for the first quarter of 2027. The Merkle Tree design, credited to Google and announced in February, replaces the chain of quantum-vulnerable signatures with compact Merkle proofs, where a CA signs a single tree head representing millions of certificates and the browser usually handles a lightweight landmark proof, dropping handshake data to about 40 KB, which Ars Technica states is about the same as is processed now. A separate stated benefit is that transparency logging becomes part of issuance, quoted from Cloudflare engineer Mari Galicer as transparency becoming a requirement for operation rather than an add-on. Cloudflare's own post was not resolved after two slug attempts, so the detail here is Ars Technica quoting Cloudflare engineers.
- **Why it matters:** Handshake size, not the algorithm, is the practical blocker for post-quantum certificates, and a dated issuance target gives operators something to plan against.

### OpenZL ships a native LZ engine with decompression over 2x faster than Zstandard

- **Category:** Dev tools
- **Status:** confirmed
- **Sources:** [primary](https://openzl.org/blog/2026-09-29-lz-in-openzl/), [discussion](https://www.reddit.com/r/programming/comments/1wuf5lf/openzl_v02_decompression_2x_faster_than_zstandard/)
- **Blurb:** OpenZL's own LZ engine decompresses over 2x faster than Zstandard, with benchmark tables run on v0.3.0.
- **Summary:** The native LZ engine ships starting in v0.2.0, and the published benchmark tables were run with v0.3.0, reporting decompression over 2x faster than Zstandard across the compression level range and up to 50% faster than LZ4. Freedom from the Zstandard wire format lets offsets be bucketed by a V-optimal histogram and bitpacked with no entropy codec, decoding 2x to 3.5x faster. PivCo Huffman, a new Huffman layout by Marcin Zukowski, replaces the codec that accounted for over half of LZ decompression CPU and is enabled by default in v0.3.0. The stated tradeoff is that OpenZL compresses slightly worse than Zstandard at higher levels, because it does not yet support repeat offsets.
- **Why it matters:** The gains come from two independent sources, an unconstrained wire format and a new Huffman layout, so only the first is limited to pipelines that control both ends.

### Rust 1.99.0 stabilizes C-ABI variadic functions written in Rust

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/), [discussion](https://news.ycombinator.com/item?id=49920917)
- **Blurb:** Rust 1.99.0 stabilizes defining C-ABI variadic functions in Rust, removing a reason to keep a C shim in FFI.
- **Summary:** The release announcement states that Rust 1.99.0 stabilizes variadic functions using the C ABI, so a Rust function can take a variable argument list rather than only call one. The same release stabilizes the raw-pointer layout queries `mem::size_of_val_raw`, `mem::align_of_val_raw`, and `Layout::for_value_raw`, along with `Vec::into_parts` and `Vec::from_parts`, `Box::into_non_null` and `Box::from_non_null`, `std::fs::set_times`, and `IntoIterator` for boxed arrays. - **Why it matters:** Rust could already call C variadics, and defining them removes a reason to keep a C shim at FFI boundaries that expose printf-style entry points.
