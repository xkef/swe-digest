## Top stories

### An expired 5 euro domain gave a researcher DNS control of three territories' ENUM zones, and logged about 209,000 phone-number queries before the NCSC took it over

- **Category:** Security
- **Status:** confirmed
- **Sources:** [lina.sh write-up](https://lina.sh/blog/hijacking-e164-arpa), [HN discussion](https://news.ycombinator.com/item?id=49387570)
- **Summary:** Three territories' zones under `e164.arpa` were delegated to a nameserver whose own domain had lapsed, so registering that expired domain for 5 euros put the author, lina, in authoritative control of every name beneath them. The post reports 100,170, 99,902 and 9,133 queries across the zones, roughly 209,000 in total, and a footnote states that a friend ran a second nameserver without logging, so the published figures are roughly half of what arrived. The national cyber security centre subsequently took the domain over. The logs are ENUM DNS lookups, and the step from those lookups to conclusions about who was placing calls is the author's inference rather than something the query data establishes.
- **Comments:** HN commenter tosti quotes the passage drawing that conclusion and calls it a jump from the logged data. Commenter toast0 states ENUM is less dead than the post assumes, because number-porting services still issue ENUM queries against private nameservers reached over VPN.
- **Why it matters:** A zone can be delegated to a nameserver whose own domain has lapsed, which turns the 5 euro registration of that expired nameserver domain into control of every name beneath the zone.

### JSONata patches three critical expression-evaluation escapes that reach arbitrary code execution, cleared by 2.2.1 and 1.8.8

- **Category:** Security
- **Status:** confirmed
- **Sources:** [GitHub advisory GHSA-66mm-25pp-rfff](https://github.com/advisories/GHSA-66mm-25pp-rfff), [GitHub advisory GHSA-2943-5xfg-gq5f](https://github.com/advisories/GHSA-2943-5xfg-gq5f), [GitHub advisory GHSA-8gq3-vp5j-2grp](https://github.com/advisories/GHSA-8gq3-vp5j-2grp), [JSONata 2.2.1 release](https://github.com/jsonata-js/jsonata/releases/tag/v2.2.1)
- **Summary:** Three separate advisories, each rated CVSS v4 9.3, describe an escape from JSONata's expression evaluation that reaches arbitrary code execution in the host process, and the advisory texts carry working proof-of-concept expressions. The affected ranges are `>= 2.0.0, < 2.2.1` and `< 1.8.8` for the two linked above, and `<= 1.8.7` plus `>= 2.0.0, < 2.2.0` for the third, GHSA-8gq3-vp5j-2grp and CVE-2026-77413, which this run found through the advisories API. The patches are older than the advisories: 2.2.1 was released on 2026-05-19 and 1.8.8 on 2026-07-16, and the advisories were published in the jsonata-js/jsonata repository on 2026-07-13. What happened on 2026-08-21, within a few minutes of each other from 20:57 UTC, is that all three entries reached the GitHub Advisory Database.
- **Why it matters:** A service that evaluates a user-supplied JSONata expression on a version below 2.2.1 or 1.8.8 hands the sender code execution in the host process, and 2.2.0 is not enough, because it clears CVE-2026-77413 and leaves the other two.

### A traced RTX 4090 global load measures 15.4 ns at L1, 127.4 ns at L2 and 255.4 ns at DRAM, with the L1 set function and L2 slice hash reverse engineered

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [doubleword.ai post](https://blog.doubleword.ai/what-happens-when-a-gpu-reads-memory), [HN discussion](https://news.ycombinator.com/item?id=49390308)
- **Summary:** The post traces a single global load through the memory path of an RTX 4090 and puts a measured latency on each level, 15.4 ns when it hits L1, 127.4 ns at L2 and 255.4 ns when it reaches DRAM. It also reverse engineers two mappings Nvidia does not document, the function that selects an L1 set and the hash that assigns an address to an L2 slice. The probes and the clock settings used to take the measurements are published alongside the numbers.
- **Why it matters:** The post publishes its probes and clock settings, so the latencies and the slice mapping can be reproduced on another card rather than taken from vendor documentation that does not cover them.

### Hydra's instantiate call turns untrusted config into code execution, with hydra-core 1.3.3 and earlier affected

- **Category:** Security
- **Status:** confirmed
- **Sources:** [GitHub advisory GHSA-2cp2-2r3c-7p7r](https://github.com/advisories/GHSA-2cp2-2r3c-7p7r), [Hydra 1.3.4 release](https://github.com/hydra-ecosystem/hydra/releases/tag/v1.3.4)
- **Summary:** Hydra's instantiation path resolves the `_target_` key of a configuration to a callable and invokes it, so a configuration file an attacker controls becomes code execution in the process that loads it. The advisory gives the affected range as hydra-core 1.3.3 and earlier, patched in 1.3.4. The 1.3.4 fix is a blacklist, and the advisory states explicitly that it is defense in depth rather than a complete boundary.
- **Why it matters:** The advisory states the 1.3.4 blacklist is defense in depth and not a complete boundary, so upgrading is not the whole fix and the calling application still has to validate `_target_` against a trusted allowlist.
- **Follow-up:** Track whether an allowlist-based instantiation model ships in a later Hydra release.

### Odin's inline assembler type checks assembly against per-instruction operand forms and returns multiple results from one template

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [gingerbill.org article](https://www.gingerbill.org/article/2026/08/20/designing-odins-inline-asm/), [HN discussion](https://news.ycombinator.com/item?id=49376769)
- **Summary:** The compiler uses each operand's Odin type to decide register class and operand width, then checks whether the instruction form accepts it, which replaces GCC-style constraint strings and positional operand numbers. Because Odin has multiple return values, `rdtsc` and `cpuid` destructure like an ordinary procedure call instead of writing through out parameters.
- **Why it matters:** Operand class and width come from the type system rather than from a constraint string, so an operand the instruction form does not accept is rejected at compile time.

### WarpStream's Kafka producer proxy holds each response to WarpStream's own write latency, so a mistuned producer fails during the proxy phase instead of after the cutover

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [WarpStream blog post](https://www.warpstream.com/blog/orbit-kafka-auto-migration), [HN discussion](https://news.ycombinator.com/item?id=49389769)
- **Summary:** During migration the proxy delays each produce response to match WarpStream's own write latency, so a producer with timeouts too tight for the destination fails while the source cluster is still authoritative. The cutover gate uses time lag rather than offset lag, because time lag translates directly into how long producers sit retrying with writes held in client buffers. A topic that does not drain inside the timeout rolls back to the proxy state on its own, and the post is written by the vendor selling the destination cluster.
- **Why it matters:** Gating the cutover on time lag rather than offset lag measures the quantity that decides whether producers stall, which is how long the backlog takes to drain rather than how many records it holds.
