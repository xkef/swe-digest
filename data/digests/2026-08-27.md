### Trail of Bits reports GPT-5.6-Cyber escaped a QEMU/KVM sandbox three times

- **Category:** Security
- **Status:** confirmed
- **Sources:** [Trail of Bits](https://blog.trailofbits.com/2026/08/26/vms-wont-contain-cyber-capable-agents/), [HN 49450188](https://news.ycombinator.com/item?id=49450188)
- **Blurb:** Trail of Bits reports GPT-5.6-Cyber broke out of a QEMU/KVM sandbox three times, the last chain using four host vulnerabilities.
- **Summary:** Trail of Bits ran GPT-5.6-Cyber against a QEMU/KVM VM hosted on a Debian 12 dev machine and reports three distinct escapes, while a Firecracker sandbox held. The first hit the host kernel through CVE-2026-53359, named Januscape, and the second used the libslirp 4.7.0 that Debian 12 ships, carrying CVE-2026-9539, combined with an unmarked bugfix commit. Before the third the author rebuilt libslirp and QEMU from upstream, and the agent still chained three 0-days with one KVM bug patched upstream but absent from the distribution kernel: a QEMU VAPIC unchecked ROM alias overlapping locked SMRAM, an unsynchronized shadow page, a stale level-2 role in `paging64_invlpg`, and a libslirp mixed-fragment-IHL ICMP reassembly bug.
- **Why it matters:** An ordinary VM is no longer a sufficient boundary for a capable coding agent, and the report concludes that the machine doing the sandboxing needs a rapidly updating distribution rather than a slow-moving stable one.

## ML research

### SMITH trains tool creation and tool use in one policy

- **Category:** Paper
- **Status:** confirmed
- **Sources:** [arXiv 2608.24571](https://arxiv.org/abs/2608.24571)
- **Blurb:** SMITH trains one policy to write and call its own tools, letting a 4B Qwen3 outscore an untrained 30B-A3B tool-writer.
- **Summary:** The paper presents SMITH, for Schema-grounded Multi-task Iterative Tool Honing, which trains tool creation and tool use in a single policy rather than prompting a frozen model at inference time. Training uses separate reward axes for schema, code, and outcome. The authors report a 4B Qwen3 reaching 79.8 macro-average accuracy against an untrained 30B-A3B tool-writer.
- **Why it matters:** Existing tool-creation systems never tell the writer that the schemas it emits are schemas it will have to invoke, and the reported gains come from closing that loop.

## Security

### Check Point reverse engineers Defender's boot-time removal driver into a kernel file and registry primitive

- **Category:** Security
- **Status:** confirmed
- **Sources:** [Check Point Research](https://research.checkpoint.com/2026/btr-reforged-weaponizing-defenders-remediation-driver-as-a-kernel-operation-primitive/), [HN 49444878](https://news.ycombinator.com/item?id=49444878)
- **Blurb:** Check Point turned Defender's signed boot-time removal driver into an arbitrary kernel file and registry write primitive.
- **Summary:** Check Point published research on 2026-08-20, by Jiri Vinopal, on BTR.sys, a Microsoft-signed driver that ships embedded as a PE resource inside MpEngine.dll and is dropped under `System32\drivers` with a randomized name when a Defender remediation needs a reboot. The driver exposes no IOCTL interface and instead reads an RC4-encrypted configuration from an alternate data stream named by its service key's Args value, using a hard-coded 256-byte key in `.rdata` that Check Point reports is consistent across driver versions, with integrity checked by a CRC-32 variant that omits the final inversion. Check Point maps the transaction format and implements six action ids in a tool it calls BTR_CLI, including move with an arbitrary destination and registry set-value, which it describes as arbitrary file write and arbitrary registry write usable for persistence or for disabling security controls.
- **Why it matters:** Loading a kernel driver requires administrative rights, so this is a post-exploitation and EDR-bypass path built on a signed Windows built-in rather than a privilege escalation, and it needs no memory-corruption bug and no vulnerable third-party driver.
- **Follow-up:** Whether Microsoft changes the driver's configuration handling or the hard-coded key, since there is no CVE and no patch to apply.

## Engineering posts

### Cloudflare cuts 1.1.1.1 DNS cache memory by 56 percent with five Rust layout changes

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [Cloudflare blog](https://blog.cloudflare.com/dns-cache-memory-optimization-1111/), [HN 49468083](https://news.ycombinator.com/item?id=49468083)
- **Blurb:** Cloudflare cut 1.1.1.1 DNS cache memory per entry by over half with five Rust layout changes, freeing about 100 TB.
- **Summary:** Cloudflare describes five layout changes to the DNS cache behind 1.1.1.1, which it states holds over 250 billion entries, so one wasted byte per entry costs over 250 GB across the fleet. The changes replace `Vec` and `String` with `Box<[T]>` and `Box<str>` to drop the unused capacity field, saving 8 bytes per field and 64 bytes per entry, merge the answer, authority, and additional lists into one list with u16 section offsets for 28 bytes, drop the record owner name when it equals the queried name and restore it from the cache key at read time, and box the large enum variants so A and AAAA records stop paying the 144-byte NAPTR-sized footprint. Cloudflare reports per-entry memory down over 50 percent, about 100 TB freed, insert throughput up 43 percent, and lookup latency down 19 percent, and states the benchmark approximates production rather than reproducing it, with resident memory measured across production instances during rollout.
- **Why it matters:** These are ordinary Rust layout decisions any service holding many small records can apply, and here they cut memory while throughput rose rather than fell.
