### Chrome Web Store removes all remaining Manifest V2 extensions, including uBlock Origin

- **Category:** Dev tools
- **Status:** confirmed
- **Sources:** [primary](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline), [report](https://webiterate.dev/google-removed-extensions-ublock-origin-108/), [discussion](https://news.ycombinator.com/item?id=49514878)
- **Blurb:** Google's Manifest V2 timeline records 2026-08-31 as removal of all remaining MV2 extensions from the Chrome Web Store.
- **Summary:** Google's Manifest V2 support timeline records the 2026-08-31 milestone as removal of all remaining Manifest V2 extensions from the Chrome Web Store, ending a deprecation Google began in January 2022 when the store stopped accepting new public MV2 submissions. Per that page, MV2 extensions installed on Chrome 138 or earlier stay installed but cannot receive updates and cannot be reinstalled from the store once removed. The secondary report records Brave hosting four MV2 extensions on its own backend: AdGuard, uBlock Origin, uMatrix, and NoScript.
- **Why it matters:** The Chrome Web Store is the dominant extension marketplace for Chromium-based browsers, so users of other Chromium browsers can no longer discover or install these extensions there even where the browser still supports MV2.
- **Follow-up:** Track whether other Chromium browsers publish MV2 distribution paths of their own.

### PyPI stops counting metadata requests as package downloads

- **Category:** Dev tools
- **Status:** confirmed
- **Sources:** [primary](https://blog.pypi.org/posts/2026-08-31-download-counts/), [discussion](https://news.ycombinator.com/item?id=49515412)
- **Blurb:** PyPI now counts only .whl, .tar.gz and .zip fetches, after about 39 percent of urllib3 counts were other objects.
- **Summary:** PyPI shipped a change on 2026-08-24 so that only requests ending in `.whl`, `.tar.gz`, or `.zip` produce a download record, where previously every object under a release prefix counted, including PEP 658 `.metadata` sidecars that installers fetch to read wheel metadata without downloading the wheel, `.asc` signatures, `.egg` uploads, and formats frozen under PEP 527. A published query over urllib3 for 2026-08-18 to 2026-08-25 shows about 39 percent of counted objects were not distribution files, and daily totals across PyPI, previously cycling between roughly 4.5 billion at weekends and a little over 7 billion midweek, step down after the change. PyPI states the discontinuity at 2026-08-24 in the public BigQuery dataset is expected and permanent, that historical rows are unchanged, and that download counts are not a proxy for popularity or criticality.
- **Why it matters:** Anything reading those counts, including pypistats.org, changes shape at a fixed date, so any comparison spanning 2026-08-24 is invalid.
- **Follow-up:** Track whether range requests, which still count a 206 the same as a 200, are addressed, since PyPI states that work is unscheduled.

## Agentic coding

### Google Antigravity adds a /boost multi-agent reasoning mode

- **Category:** Agentic coding
- **Status:** confirmed
- **Sources:** [primary](https://antigravity.google/docs/boost/), [discussion](https://news.ycombinator.com/item?id=49517537)
- **Blurb:** Google Antigravity's /boost mode splits a task across subagents in isolated worktrees, then validates against test suites.
- **Summary:** The documentation describes a three-phase pipeline. An orchestrator forms a strategy and splits the task, dispatches implementation and investigation subtasks to subagents running in ephemeral isolated worktrees, then validates the combined result against full test suites and feeds failed assertions back for another round. Boost is documented as sitting between the default single-agent loop and the multi-day Teamwork mode, with a stated horizon of seconds to hours, and it is limited to paid plans on Antigravity 2.0 and the CLI. Subagents inherit the workspace file access and command permission policies rather than bypassing them.
- **Why it matters:** Subagents inheriting the parent's file access and command permissions is the detail that decides whether a fan-out mode widens the blast radius of an agent run.

METR states the post covers external actors attempting unauthorized access to its systems rather than AI agents hacking during its evaluations, and that an initial scan found no evidence of any agents hacking third parties during its evaluations.
- **Why it matters:** METR holds pre-deployment evaluation access to frontier models, so a compromise of its own infrastructure is a supply chain question for the labs that grant that access.

### PEP 805 proposes thread-scoped object sharing, and Guido van Rossum says he wishes Python had stuck with the GIL

- **Category:** Languages
- **Status:** developing
- **Sources:** [primary](https://discuss.python.org/t/pep-805-safe-parallel-python/108670?page=4), [discussion](https://news.ycombinator.com/item?id=49508906)
- **Blurb:** Mark Shannon's PEP 805 would give objects a shareable state, and Guido van Rossum says he wishes Python had kept the GIL.
- **Summary:** The thread on Mark Shannon's PEP 805, Safe Parallel Python, is active through 2026-09-01, and the proposal gives objects a `__shareable__` state of LOCAL, PROTECTED, IMMUTABLE, or SYNCHRONIZED, raises on illegal cross-thread access, groups threads so that the Main ThreadGroup serializes execution and parallelism requires explicit membership, and was updated on 2026-08-27 to use copying instead of relying on unique references, which Shannon states should make it implementable by MicroPython and GraalPython. Objections in the thread are concrete: Anders Ha notes Kotlin/Native abandoned a comparable object-graph freezing model and went free-threaded, David Ellis notes lazy imports and submodules make module freezing a poor fit while mocking relies on mutating modules, and Inada Naoki argues extension modules still need guarantees that a locked list or dict has not changed across a Python call. Guido van Rossum wrote on 2026-08-27 that users may violate the do-not-mutate-shared-objects rule by accident, and separately that personally he wishes they had stuck with the GIL because everything was simpler.
- **Why it matters:** The PEP would change how every Python thread reaches an object, it is framed as building on PEP 703 rather than competing with it, and nothing is decided.
- **Follow-up:** Track whether PEP 805 reaches a Steering Council decision and how it lands against PEP 703 free-threading.

## Infrastructure

### Tailscale releases tailcat, its data plane without its control plane

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [primary](https://tailscale.com/blog/tailcat), [discussion](https://news.ycombinator.com/item?id=49517420)
- **Blurb:** Brad Fitzpatrick released tailcat, a Go tool using Tailscale's WireGuard and DERP data plane with no control plane.
- **Summary:** Brad Fitzpatrick published tailcat on 2026-08-31, an open source Go package and CLI that uses Tailscale's WireGuard, NAT traversal, and DERP data plane with no control plane, no accounts, no user-visible IP addresses, no admin controls, and no root requirement. A server generates a keypair, picks a DERP server, and emits an address string of the form `tc` plus base64 of CBOR over the public key and DERP bootstrap information, shared out of band or through a DNS TXT record, and the client sends a MEOW message over DERP to join the netmap then opens TCP over an embedded userspace stack atop WireGuard. Default mode pipes to stdout like netcat, a client mode runs a local SOCKS server and a child process, and NAT traversal attempts a direct connection with DERP relaying as fallback, rate-limited on Tailscale-hosted DERP and under the operator's own limits when self-hosted.
- **Why it matters:** It gives ephemeral and untrusted machines a NAT-traversing transport with no account and no admin plane, and Fitzpatrick states he wrote it in 2023 and cites sandboxed coding agents as the use case that brought it back.

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [primary](https://aws.amazon.com/blogs/aws/amazon-ec2-r9g-and-r9gd-instances-powered-by-aws-graviton5-processors-are-now-generally-available/), [discussion](https://news.ycombinator.com/item?id=49515659)
- **Blurb:** AWS made the Graviton5-based R9g and R9gd instances generally available, claiming up to 25 percent more compute per vCPU.
- **Summary:** AWS made the memory-optimized R9g and R9gd instances generally available on 2026-08-31, stating up to 25 percent higher compute performance per vCPU over Graviton4-based R8g, DDR5 at 8800 MT/s up from 5600 MT/s, a 5x larger L3 cache, up to 2x higher network and EBS bandwidth at the largest sizes reaching 100 Gbps network and 72 Gbps EBS on the 48xlarge, and up to 3x higher packet-processing performance. Both families offer 11 sizes from medium to metal-48xl, topping out at 192 vCPUs and 1536 GiB, support Instance Bandwidth Configuration to shift 25 percent of allocation between EBS and VPC networking, and carry the Nitro Isolation Engine introduced with C9g and M9g, which AWS describes as using formal verification of isolation. R9gd adds local NVMe SSD, AWS states most applications migrating from R8g need no code changes, and availability is US East (N. Virginia, Ohio), US West (Oregon), and Europe (Frankfurt).
