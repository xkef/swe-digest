## Top stories

### One extension reached the built-in AI assistants in Chrome, Edge, Comet, Opera Neon and Claude in Chrome

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://forever.security/blog/bragjack-hijacking-5-browsers-via-built-in-ai-assistants/), [discussion](https://news.ycombinator.com/item?id=49729492)
- **Blurb:** Forever Security hijacked the browser agent in Edge, Comet, Opera Neon and Claude in Chrome, and ran code inside Chrome's assistant.
- **Summary:** The disclosure, which the publisher calls BragJack, describes an ordinary extension reaching the assistant built into Edge, Comet and Opera Neon through the page the browser trusts to command it, using only content-script and request-rewriting permissions an extension already holds, and needing no prompt injection and no user click. The impact table marks browser agent hijack as not achieved on Chrome, where the demonstrated result is code execution inside the assistant component with local file access, microphone and camera access, a profile leak and screenshots, and the fifth case, Claude in Chrome, is an extension rather than a browser, which the post calls an extension exploiting an extension and much less of a security risk and which Anthropic rated medium severity. The post lists the ids CVE-2026-0628 and CVE-2026-55945 in a table whose columns do not survive text extraction, so neither id can be assigned to a specific product from this source, and it names no affected version and no fixed version for any of the five.
- **Why it matters:** The extension-to-browser boundary fails here through the agent's own trusted input path rather than through the browser, so an extension's stated permissions no longer bound what it can make the assistant do.
- **Follow-up:** Track fixed versions from Google, Microsoft, Perplexity, Opera and Anthropic, and the per-browser assignment of CVE-2026-0628 and CVE-2026-55945.

### Unicode 18.0 adds 13,007 characters and changes line breaking, segmentation and spoofing rules

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://www.unicode.org/versions/Unicode18.0.0/), [enumerated versions](https://www.unicode.org/versions/enumeratedversions.html), [discussion](https://www.reddit.com/r/programming/comments/1wifzlx/unicode_1800_has_been_released/)
- **Blurb:** Unicode 18.0 adds 13,007 characters and revises the line-breaking, grapheme segmentation and spoofing-detection rules.
- **Summary:** The version page states Unicode 18.0.0 adds 13,007 characters for a repertoire of 172,808. The annex changes are the upgrade work: UAX #14 changes rule LB12a and moves FIGURE DASH, EN DASH and SOFT HYPHEN between line-break classes, UAX #29 revises grapheme cluster rule GB9c, and UTS #39 tightens spoofing rule A1 by removing the allowance for transparent characters between ZWNJ and the following joining character. The version page is dated 2026-09-16 and still carries preliminary-draft and beta-review notices over several sections including the UCD data files, while the enumerated-versions table lists 18.0.0 as a 2026 release alongside every prior released version.
- **Why it matters:** Existing text wraps, segments and gets flagged differently once a library picks up the new data, without any change to the text itself.
- **Follow-up:** Check that the 18.0.0 version page drops its preliminary-draft and beta-review notices, and read the release announcement post on blog.unicode.org.

## ML research

### BITCOS packs ternary LLM weights below the 1.585-bit reference by exploiting zero density

- **Category:** Paper
- **Status:** developing
- **Sources:** [primary](https://arxiv.org/abs/2609.16338), [discussion](https://news.ycombinator.com/item?id=49732931)
- **Blurb:** BITCOS packs ternary LLM weights below the 1.585-bit reference by exploiting zero density, reaching 1.485 bits per weight.
- **Summary:** The authors measure the symbol distribution of 29 ternary models, find zeros reach 51.5 percent of weights, and replace five-trit packing, which rounds to 1.625 bits per weight, with a presence bitmap plus a compacted sign vector costing 2 minus the zero density. They report smaller storage on 26 of the 29 models, 1.485 bits per weight on the sparsest, and measured end-to-end decode gains up to 1.18 times on CPUs and 1.27 times on Xe2 GPUs. The preprint is not peer reviewed, and the optimized unpacking sequences target AVX-512, AVX2 and Intel Xe2 GPUs and are unreproduced.
- **Why it matters:** The deployment cost of a ternary model turns on the storage layout rather than on the information-theoretic bound the format is usually quoted against.

## Security

### GPUThor reports the first Rowhammer exploits against ECC-protected NVIDIA GPUs

- **Category:** Security
- **Status:** developing
- **Sources:** [primary](https://arxiv.org/abs/2609.16546), [discussion](https://news.ycombinator.com/item?id=49725638)
- **Blurb:** Researchers report Rowhammer bit flips that ECC cannot correct on four NVIDIA workstation GPUs, at far higher rates than prior work.
- **Summary:** The authors reverse engineer memory-access coalescing to hammer aggressor rows harder than decoy rows and stretch hammering patterns across refresh intervals, reporting 500 to 23,500 times more bit flips than prior GPU Rowhammer work, which produced tens to hundreds. They state this induces uncorrectable double and triple bit flips on A4000, A4500, A5000 and A6000 parts. The paper states it will appear at CCS 2026, no CVE is assigned, and NVIDIA has published nothing on it.
- **Why it matters:** Denial of service and privilege escalation become practical on shared GPU hosts where ECC was the assumed mitigation.
- **Follow-up:** Track an NVIDIA statement, a CVE assignment, and any independent reproduction on the named parts.

## Apple platforms

### A twenty-line Mach IPC sequence panicked macOS and iOS kernels until a fix shipped in the 27 releases

- **Category:** Apple
- **Status:** confirmed
- **Sources:** [primary](https://seriot.ch/security/ipc_panic.html), [discussion](https://news.ycombinator.com/item?id=49729749)
- **Blurb:** About twenty lines of Mach IPC code let any local process panic macOS and iOS kernels until a fix shipped on 2026-09-14.
- **Summary:** Requesting a no-senders notification on a port and then destroying that port made the kernel take the same port lock twice, so ipc_port_destroy never ran and the waitq lock timed out into a panic. The author reports it is reachable by any local unprivileged process in about twenty lines of C. Apple classified it as non-security because it discloses no data and grants no privilege, assigned no CVE, and credited the fix in the macOS 27, iOS and iPadOS 27, watchOS 27 and visionOS 27 release notes on 2026-09-14.
- **Why it matters:** A local denial of service that costs twenty lines and needs no privilege is reachable from any sandboxed app process, and the release notes are the only place the fix is visible.

## Infrastructure

### PlanetScale ships TIN, a full-text search index for Postgres built on ctid postings

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [primary](https://planetscale.com/blog/introducing-tin), [discussion](https://news.ycombinator.com/item?id=49729383)
- **Blurb:** PlanetScale released TIN, a Postgres full-text index that uses the ctid as the document identifier, GA on its own databases.
- **Summary:** TIN uses the Postgres ctid directly as the document identifier, encoded as page-level and offset-level bitmaps sized to AVX2 and AVX-512 registers, which removes the identifier-to-ctid mapping that ParadeDB and pg_textsearch maintain and returns matches in heap order. The published benchmarks are vendor-run on a single 85 GB corpus and report 8 to 541 times the throughput of those alternatives. The release is GA only for PlanetScale Postgres and Neki databases rather than an extension to install elsewhere.
- **Why it matters:** The design removes a mapping layer that every comparable Postgres full-text extension has to keep consistent with the heap.
- **Follow-up:** Track whether TIN becomes installable outside PlanetScale and whether any third party reproduces the throughput figures.

## Engineering posts

### Post-training a 4B model to write Postgres query plans reports a 44.7 percent latency cut on 113 join-heavy queries

- **Category:** Engineering post
- **Status:** developing
- **Sources:** [primary](https://rohanbansal.com/qorl), [discussion](https://news.ycombinator.com/item?id=49731285)
- **Blurb:** A 4B model post-trained to write Postgres query plans cut summed latency 44.7 percent on 113 join-heavy benchmark queries.
- **Summary:** The write-up publishes the rig rather than only a score: supervised fine-tuning distilled from about five hundred frontier-model trajectories, then a GRPO variant whose reward is measured execution time against Postgres's own plan, with vLLM and the trainer on a rented two-GPU node and four Postgres containers isolated to limit page-cache contention. The starting 4B model could not produce a plan at all for 99 of the 113 queries. The reported result is a 1.81 times geometric-mean speedup and a 44.7 percent summed latency reduction on the Join Order and Cardinality Estimation benchmarks, measured by the author alone.
- **Why it matters:** The reward is wall-clock execution time against the planner's own choice, which is a reproducible target rather than a proxy metric.
