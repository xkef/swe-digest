### Zig 0.17.0 reworks the build system and redefines @bitCast

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://ziglang.org/download/0.17.0/release-notes.html), [discussion](https://news.ycombinator.com/item?id=49938521)
- **Blurb:** Zig 0.17.0 reworks the build system and redefines @bitCast, which the release notes say can break code without a compile error.
- **Summary:** The release notes record 5 months of work and 925 commits from 206 contributors, introduce the Build Server Protocol, and describe an ELF linker improved to the point where the notes expect incremental compilation to work for everyone on x86_64-linux. `@cImport` is removed, C translation moves to the external ZSF translate-c package, and `std.Build.Step.TranslateC` is deprecated. The redefined `@bitCast` is fully endian-agnostic and largely matches the old behavior on little-endian targets, casts involving `extern struct` and `extern union` are now rejected outright with `@ptrCast` given as the replacement for type punning, and the notes state the change can break existing code without triggering a compile error.
- **Why it matters:** Upgrading requires auditing every `@bitCast` touching array or vector types, because the release notes state the change can break existing code without triggering a compile error.

## ML research

### AutoCompact trains a coding agent to decide when to compact its own context

- **Category:** Paper
- **Status:** confirmed
- **Sources:** [primary](https://arxiv.org/abs/2610.02163)
- **Blurb:** AutoCompact folds context compaction into the policy, reporting a 9.2-point pass-rate gain on SWE-bench Verified.
- **Summary:** Context management in long-horizon coding agents is usually a harness heuristic outside the model, and AutoCompact folds the decision into the policy: when to compact, what working state to keep, and how to resume. Training data comes from running the base agent, having a judge review its compaction decisions, summaries, and post-compaction actions, then replacing flawed outputs with corrected ones before execution, with supervised fine-tuning followed by joint RL on coding and compaction under task-success rewards. The paper was posted 2026-10-01 and reports absolute pass-rate gains of 9.2% on SWE-bench Verified and 5.0% on SWE-PolyBench Verified, with no independent reproduction.
- **Why it matters:** The reported gains hold across inference budgets, which suggests context compaction is better trained into the model than configured in the harness.

### Exploitation begins against a Rejetto HFS signing-key flaw found with Anthropic's Mythos

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://github.com/advisories/GHSA-xxrm-3f86-v97j), [fix release](https://github.com/rejetto/hfs/releases/tag/v3.2.1), [research index](https://horizon3.ai/category/attack-research/), [exploitation report](https://www.theregister.com/security/2026/10/03/anthropics-super-bug-hunting-model-mythos-is-hardcore-good-at-math-as-latest-vuln-under-attack-shows/5300933), [discussion](https://news.ycombinator.com/item?id=49946226)
- **Blurb:** Attackers are exploiting a Rejetto HFS flaw rated CVSS 9.3 that recovers the session signing key and forges an admin cookie.
- **Summary:** GHSA-xxrm-3f86-v97j records that Rejetto HFS 3.0.0 through 3.2.0 derives its session-cookie signing key from the non-cryptographic `Math.random()` generator and discloses outputs of that generator to unauthenticated clients during login, so an attacker can collect a small number of login responses, reconstruct the generator state, recover the key, and forge a valid administrator session cookie, which the advisory states leads to full administrative access and remote code execution through the `server_code` configuration feature. The advisory scores it CVSS v4 9.3 under CWE-338, carries the 3.0.0 through 3.2.0 range in its description text while its structured affected and patched fields read Unknown, references the v3.2.1 release tag as the fix, and was published 2026-07-13, well behind the current 3.3.4 of 2026-09-30. The Register quotes VulnCheck's Patrick Garrity describing exploitation beginning on the night of 2026-10-01 from a single China-hosted address against hosts in the United States and Japan, followed on 2026-10-02 by four attempts from two United States addresses in one subnet that appear to be a proxy. Garrity's tracker attributes 286 CVE records to Mythos and Project Glasswing, and he states this is the second of those known to be exploited. The Horizon3 attack research index carries a disclosure entry dated 2026-09-30 stating its researchers used Anthropic's Mythos to find the chain of cryptographic weaknesses, recover the signing key, forge an admin session, and reach remote code execution, and the firm's own write-up was not reachable from this environment.
- **Why it matters:** HFS 3.0.0 through 3.2.0 are affected and 3.2.1 fixes it, so instances on the current 3.3.x line are already clear and the exposure is limited to unmaintained deployments, where the outcome is remote code execution rather than data exposure alone.
- **Follow-up:** Watch for the Horizon3 write-up, and for the timeline discrepancy between The Register's 2026-09-30 discovery framing and the advisory's 2026-07-13 publication date.

### Five cross-tenant elevation-of-privilege flaws in Azure Logic Apps API Connections

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.binarysecurity.no/posts/2026/10/one-root-case), [discussion](https://news.ycombinator.com/item?id=49932619)
- **Blurb:** Binary Security details five cross-tenant privilege flaws in Azure API Connections, where two fixes reopened each other.
- **Summary:** Haakon Wik Gulbrandsrud of Binary Security published the third part of his Azure API Connections series on 2026-10-02, and states the vulnerabilities in this part paid US$200,000 in bounties, with the series as a whole standing at five critical elevation-of-privilege findings in Azure, all now fixed. The root cause is architectural: requests reaching the shared API Management instance through ARM carry rights to every connection, so a path traversal in the DynamicInvoke payload reads another tenant's Key Vault secret, blacklisting paths left three undocumented sibling endpoints reachable, and DynamicList gave arbitrary writes against a victim's Azure SQL database until Microsoft blocked the endpoints outright. The fix validating the undocumented host.api.RuntimeUrl input ran before path normalization, so the traversal worked again, and the follow-up fix stopped validating the original RuntimeUrl path and reopened the first attack. Logic Apps API Connections is a hosted Azure service, so there is no customer-installable version range and no customer patching step: Microsoft applied all five fixes server-side.
- **Why it matters:** Consumption Logic Apps have implicit access to every Version 1 API Connection because there is no managed identity to authorize, so the backend token should be assumed to carry the full privileges of whoever created the connection.

### FTL ships v0.1.0, an operating system that implements the Linux ABI in a userspace library

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [primary](https://ftl-os.org/), [releases](https://github.com/nuta/ftl/releases), [discussion](https://news.ycombinator.com/item?id=49944912)

- **Summary:** FTL v0.1.0 implements the Linux ABI in a userspace library, placing process management, the VFS, and the TCP/IP stack in a shared library per container and leaving the kernel a hypervisor-like interface over hardware user mode.
