## Top stories

### Fortinet warns of an actively exploited FortiMail flaw with fixes pending on several branches

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.theregister.com/security/2026/10/02/fortinet-sounds-the-alarm-over-actively-exploited-fortimail-zero-day/5300803)
- **Blurb:** Fortinet confirms CVE-2026-104286 in FortiMail is under active exploitation, and fixes for several branches are still pending.
- **Summary:** Fortinet states CVE-2026-104286 in FortiMail is being exploited in the wild, and The Register reports the advisory rates it CVSS 9.8 and describes it as path traversal combined with improper handling of null characters. The affected versions listed are FortiMail 8.0.0 through 8.0.1, 7.6.0 through 7.6.6, 7.4.0 through 7.4.8, and 7.2.0 through 7.2.9, with fixes still listed as upcoming for several of those branches. The report cites the addition to the CISA known-exploited catalog with a federal remediation deadline of 2026-10-04.
- **Why it matters:** A CVSS 9.8 flaw is being exploited now across four FortiMail release branches, and operators on branches whose fixes are listed as upcoming can only apply workarounds that do not remove persistence already planted.
- **Follow-up:** Track the fixed releases for the remaining branches, and the Fortinet PSIRT advisory itself, which was not reachable at publish time.

### Linux boots on M4 Macs with all cores after WFI workarounds reach mainline

- **Category:** Linux/Kernel
- **Status:** confirmed
- **Sources:** [primary](https://yuka.dev/blog-2026-10-02-linux-m4.html), [discussion](https://news.ycombinator.com/item?id=49933869)
- **Blurb:** Linux now boots on M4 Macs with all cores after workarounds for WFI state loss landed in the mainline kernel.
- **Summary:** The write-up reports Linux booting on M4 Macs with all cores enabled once workarounds for architectural state loss on WFI landed in mainline. The author describes the hardware as losing architectural state on WFI contrary to the ARM64 specification, and the workaround shipping behind a kernel boot parameter rather than as an erratum.
- **Why it matters:** The blocking defect was silicon that loses architectural state on WFI against the ARM64 specification, and the fix shipped as a kernel boot parameter rather than an erratum, so the same path covers M4 Pro, M4 Max, and M5.

### Microsoft says attackers probed a Zimbra flaw before public disclosure

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.theregister.com/security/2026/10/01/microsoft-catches-hackers-exploiting-zimbra-bug-before-disclosure/5300543)
- **Blurb:** Microsoft says attackers probed Zimbra CVE-2026-73570 more than two weeks before the bug was publicly disclosed.
- **Summary:** Microsoft reports observing exploitation attempts against Zimbra CVE-2026-73570 more than two weeks ahead of public disclosure. The coverage states only servers running the optional SNMP package with notifications enabled are affected, that Zimbra 10.1.20 carries the fix, and that attackers used existing SSH trust between mail servers to move laterally.

## Languages and runtimes

### Rust 1.100.0 will demote both i686 Windows targets to std-only

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://blog.rust-lang.org/2026/10/02/demoting-i686-windows-targets-to-std-only/)
- **Blurb:** Rust 1.100.0 will demote both i686 Windows targets to std-only, ending toolchain installs on 32-bit Windows hosts.
- **Summary:** The Rust project announced that both i686 Windows targets drop to std-only status in Rust 1.100.0. Prebuilt standard libraries continue to ship for those targets, but the toolchain itself will no longer be installable on a 32-bit Windows host.
- **Why it matters:** Prebuilt standard libraries keep shipping, but anyone still building on a 32-bit Windows host has to move to cross-compiling from a 64-bit toolchain after Rust 1.100.
