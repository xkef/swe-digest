## Top stories

### Zod 4.6.6 published to npm with a malicious preinstall script

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://github.com/colinhacks/zod/commit/d821685ea6732436fcdf786a81d076958471e467), [registry](https://registry.npmjs.org/zod), [discussion](https://news.ycombinator.com/item?id=50052814)
- **Blurb:** A malicious `preinstall` script shipped in zod 4.6.6 and @zod/mini 4.6.6, running on plain npm install without import.
- **Summary:** A commit attributed to the maintainer account added a file named `meta.test.mjs` to both the `zod` and `@zod/mini` packages at version 4.6.6 and wired it to a `preinstall` hook, so it runs on plain `npm install` without the package being imported. The script reads an Ethereum contract through three public RPC endpoints, decodes a list of domains from the return value, fetches a `/loader` endpoint on each, writes a base64 payload to a temporary directory, and imports a second base64 stage as a `data:` URL, so the operator can repoint command and control through a chain write rather than through the package. The same commit changed the release workflow from maintainer-triggered dispatch to publishing on any version bump pushed to main, and the 4.6.6 publish carries an npm provenance attestation naming the GitHub Actions trusted publisher with approver colinhacks, which is the observable trace of that workflow change rather than a safety signal. The registry dates the 4.6.6 publish to 2026-10-11, and the version still resolves with full dist metadata and no deprecation marker, so it remains installable even though npm now lists 4.6.7 as the `latest` dist-tag.
- **Why it matters:** zod is among the most depended on packages in the JavaScript ecosystem, so any install or CI run that resolved 4.6.6 should be treated as having executed untrusted code, with no import of the package required.
- **Follow-up:** Whether the commit is confirmed as an account compromise rather than maintainer action, which the diff alone cannot distinguish.

### Cyberattack on Danfoss refrigeration software heats fridges in hundreds of French supermarkets

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.bbc.com/news/articles/crq5nzxv9q4yo), [discussion](https://news.ycombinator.com/item?id=50055304), [thread](https://news.ycombinator.com/item?id=50057551)
- **Blurb:** Attackers took over Danfoss refrigeration management software and ordered fridges in hundreds of French supermarkets to heat.
- **Summary:** The BBC reports that attackers gained control of software from the Danish engineering firm Danfoss that retailers use to manage refrigeration units remotely, and ordered units to heat up and stay hot overnight rather than run the normal short defrost cycle. Intermarche reported its fridges held 50C for six hours, and figures from individual chains point to roughly 400 of about 15,000 French stores, including more than 100 at Cooperative U, 180 across Intermarche and Netto with another 100 urgently disconnected from the internet, 80 of Carrefour's 6,000, and 5 percent of Monoprix's 400 plus, with two Alsace stores alone reporting 270,000 euros of losses. Danfoss said the affected units were older models whose security software could not be updated against a risk the firm had already identified, and the Paris prosecutor opened a cyber-crime investigation. No affected product names, firmware builds, or software versions have been published, so the scope is stated only as older models.
- **Why it matters:** Remote management software for physical plant was abused at fleet scale, and the vendor's own account points at an installed base that cannot be patched, which is an industry pattern rather than one vendor's incident.
- **Follow-up:** Whether Danfoss or French authorities publish the initial access vector, and the final count of affected stores.

### Codex CLI starts a persistent self-updating background daemon by default

- **Category:** Agentic coding
- **Status:** confirmed
- **Sources:** [primary](https://github.com/openai/codex/issues/48195), [discussion](https://news.ycombinator.com/item?id=50060694)
- **Blurb:** Codex CLI 0.157.0 starts a 374 MB self-updating background daemon that survives closing every Codex window.
- **Summary:** The issue was opened on 2026-09-25 against CLI 0.157.0, it is open, and it is reproduced on Linux, WSL2 and Windows, with `codex features disable daemon_auto_start` given as the reporter's workaround. Whether the behaviour is still the default on the current release line is unverified here, because the thread references later releases up to 0.160.1 without restating the default. Since CLI 0.157.0, opening an interactive `codex` session starts `codex app-server --managed-daemon` in its own session with no TTY, reparented to PID 1, and it survives closing every Codex window until an explicit `daemon stop` or a reboot. The CLI copies about 374 MB of platform package, including bundled `bwrap`, `zsh` and `rg`, into `~/.codex/packages/app-server-daemon/releases/` and runs the daemon from that copy, then a detached `pid-update-loop` process checks for updates five minutes after start and hourly after that, downloading releases and restarting the backend. The daemon also pins the environment of whichever session started it, so a per-invocation `HTTPS_PROXY` setting leaks into later sessions, and `daemon stop` leaves the updater running.
- **Why it matters:** The serving backend's version decouples from the binary the package manager installed, so a machine's effective Codex version is set by a background updater rather than by the fleet's package policy.
- **Follow-up:** Whether the default changes and whether `daemon stop` also stops the update loop.

## Security

### Flask session key recovered from its own cookie yields RCE across Google DevSite domains

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://simonkoeck.com/writeups/google-devsite-flask-session-pickle-rce), [discussion](https://news.ycombinator.com/item?id=50052638)
- **Blurb:** A Flask secret key stored inside its own session cookie gave pickle RCE across Google DevSite domains, paid at 90,000 dollars.
- **Summary:** Reported 2026-08-06 and fixed 2026-10-07, the OAuth flow shared by Google's developer documentation sites set a roughly 1,200 byte Flask session cookie, and because Flask signs session cookies rather than encrypting them, the payload decoded to a pickle-serialized `oauth2client.client.OAuth2WebServerFlow` object carrying the OAuth `client_id` and `client_secret` in plaintext. That client secret was also the Flask `SECRET_KEY`, so the author recomputed the itsdangerous signature offline, matched it byte for byte, then forged a session with an attacker-chosen CSRF token and a pickle under the matching flow key, which the callback passes to `pickle.loads`. Execution was demonstrated with a `time.sleep` reduce payload whose response times tracked the requested delay at 0, 3, 5 and 8 seconds, with negative controls for a missing cookie, a flipped signature byte and a missing flow entry, and because DevSite is a shared platform the key validated sessions on firebase.google.com, developer.android.com, source.android.com and docs.partner.android.com.
- **Why it matters:** The chain is four independent mistakes stacked, a credential reused as a signing key, secrets in a client-held cookie, pickle across a client boundary, and one key shared across deployments, and each is checkable in a codebase today.

### TinaCMS CLI code injection via unescaped Git branch name in generated client

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://github.com/advisories/GHSA-pwhx-cvv3-qj5c)
- **Blurb:** An unescaped Git branch name interpolated into generated TinaCMS client code executes during preview builds.
- **Summary:** `@tinacms/cli` reads the Git branch from `VERCEL_GIT_COMMIT_REF`, `GITHUB_BRANCH` or `HEAD` and interpolates it into the generated `client.ts` source with no escaping or encoding, so a branch name that `git check-ref-format` accepts can close the string literal and inject a JavaScript expression that runs when the consumer build imports the generated module. Affected versions are 2.7.0 and earlier, patched in 3.0.0, scored CVSS 8.2 and tracked as CVE-2026-108259. The advisory was published in `tinacms/tinacms` on 2026-09-16 and published to the GitHub Advisory Database on 2026-10-09, where it was also reviewed and last updated, so this is a four-week-old disclosure carried here for its pattern rather than as same-day news. The practical attack is a pull request against any project using TinaCMS with preview deployments enabled, where the build runs codegen and executes the attacker's expression with full build privileges and access to build environment variables.
- **Why it matters:** A Git ref is attacker-controlled input, so interpolating one into generated source or a URL path without `JSON.stringify` or `encodeURIComponent` turns every preview build into a code execution sink, well past this one package.
