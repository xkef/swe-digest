### CyberPanel ships a hard-coded WebTerminal JWT secret that yields an unauthenticated root shell

- **Category:** Security
- **Status:** confirmed
- **Sources:** [research write-up](https://hellorecon.com/blog/cve-2026-67614-cyberpanel-webterminal-jwt-root-shell), [HN submission](https://news.ycombinator.com/item?id=49311252)
- **Blurb:** Researchers found CyberPanel 2.4.2 through 2.4.6 with a hard-coded WebTerminal JWT secret yielding unauthenticated root on port 8888.
- **Summary:** Researchers report that the HS256 signing key for CyberPanel's WebTerminal was a string literal in the source tree and identical on every install from 2.4.2 through 2.4.6, and that the WebSocket handler reads the account to log in as from the token's own ssh_user claim, so any reachable port 8888 on those versions is an interactive root shell with no credentials and no failed-login trail. Versions 2.4.7 through 2.4.9 and 3.0.0 generate the secret per install, so reaching root on those releases means chaining CVE-2026-67613, which the write-up states is scored as requiring an authenticated administrator, making that path a privileged-admin-to-root escalation rather than an unauthenticated one. The researchers state the maintainer confirmed only 3.0.1 closes the full chain, while NVD metadata reads before 3.0.0, and the write-up cites the VulnCheck CNA record, the NVD entry for CVE-2026-67614 and CyberPanel coordinated-disclosure issue 1858 as its primaries.
- **Why it matters:** The fully unauthenticated root shell is confined to 2.4.2 through 2.4.6, and teams that upgraded to 3.0.0 on the strength of the published version range still need 3.0.1 to close the chain.

### A contract-grade verifier finds 39.5 percent of already-accepted LLM-generated GPU kernels broken beyond tolerance

- **Category:** Paper
- **Status:** confirmed
- **Sources:** [primary](https://arxiv.org/abs/2608.12700), [discussion](https://news.ycombinator.com/item?id=49301417)
- **Blurb:** A verifier found 39.5 percent of 2,638 LLM-generated GPU kernels already accepted by the system's own harness to be broken.
- **Summary:** The paper applies twelve adversarial gates, several of them tolerance-free, to 2,638 machine-generated kernels that a public system's own harness had already accepted, and reports 39.5 percent broken beyond any tolerance argument and 62.1 percent carrying at least one violation. It reports the standard test accepting 1,487 kernels the verifier rejects, against 14 the other way. The authors defend the result with a positive control, a threshold sweep, 98.5 percent agreement with the benchmark's own correctness code, and a hand audit.
- **Why it matters:** Reported correctness rates for kernel-generating systems rest on one loose test that runs a kernel on a few random inputs at one fixed shape, so published pass rates overstate what the kernels do.

## AI

### Anthropic describes Claude's text watermark as a SynthID-Text variant

- **Category:** AI
- **Status:** confirmed
- **Sources:** [primary](https://www.anthropic.com/news/claude-text-watermark), [discussion](https://news.ycombinator.com/item?id=49303350)
- **Blurb:** Anthropic described Claude's text watermark as a SynthID-Text variant biasing low-stakes token choices with no hidden characters or extra tokens.
- **Summary:** The method biases only low-stakes token choices by seeding the sampling randomness from a key and the preceding words, and Anthropic states there are no hidden characters, no extra tokens and no price change. Code carries less watermarking than prose because exact output leaves no free choice, and factual passages are sparser for the same reason. Anthropic states that light editing probably will not remove the mark, that a complete rewrite will, and that the detection API has not yet shipped.
- **Why it matters:** This answers the mechanism question this archive attached as a follow-up to its 2026-08-11 entry, and sets the practical limit that any rewriting stage in a pipeline erases the mark.

### Google publishes HEIR, a compiler that runs model inference on homomorphically encrypted inputs

- **Category:** AI
- **Status:** confirmed
- **Sources:** [primary](https://blog.google/security/how-google-is-making-private-ai-practical-with-homomorphic-encryption/), [discussion](https://news.ycombinator.com/item?id=49300314)
- **Blurb:** Google published HEIR, an open-source compiler running model inference on homomorphically encrypted inputs without requiring manual rewriting.
- **Summary:** HEIR is open source and converts pre-trained models rather than requiring a program to be rewritten for homomorphic encryption by hand. Google names four compiled applications: a deep learning recommendation model, credit card fraud detection, the Kitsune network anomaly detector, and a hotword detector, and states the reported latency figures are single-threaded CPU. It names hardware accelerator partners and states those latency benefits are to be demonstrated later rather than now.
- **Why it matters:** Converting a program to homomorphic encryption by hand needs a team of cryptographers, and a compiler moves that cost to models teams already have.

## Linux and kernel

### Kernel developers disagree over whether O_CREAT with O_DIRECTORY can be feature-tested safely

- **Category:** Linux/Kernel
- **Status:** developing
- **Sources:** [primary](https://lwn.net/Articles/1085617/), [discussion](https://news.ycombinator.com/item?id=49307588)
- **Blurb:** Kernel developers disagreed on O_CREAT with O_DIRECTORY feature-testing on older LTS kernels that silently created regular files.
- **Summary:** Linux has no system call that creates and opens a directory in one race-free step, which matters when another process can replace a directory between the two calls. Christian Brauner favours reusing the existing flag combination over the earlier mkdirat2 proposal, because it inherits open's name-resolution restrictions. Pedro Falcato and Christoph Hellwig argue applications cannot feature-test it safely, since older LTS kernels never took the 6.4 change that made the combination return EINVAL and the older behaviour silently created a regular file, and Neil Brown proposed a rejecting flag on openat2 instead. The series is not applied, so the final shape of the interface is unsettled.
- **Why it matters:** A silent fallback to creating a regular file on unpatched LTS kernels makes userspace adoption of the flag combination unsafe until a feature test exists.
