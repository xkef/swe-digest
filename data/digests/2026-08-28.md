### PaperCut reports active exploitation of a flaw affecting every PaperCut NG and MF version

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.bleepingcomputer.com/news/security/papercut-warns-of-ng-mf-flaw-exploited-in-zero-day-attacks/)
- **Blurb:** PaperCut says a flaw affecting every NG and MF version is under active exploitation and has shared no technical detail.

The report names no CVE and states PaperCut has not shared details about the flaw or how it is being exploited. The stated actions are the emergency patch and restricting Application Server web interfaces to trusted IP addresses, alongside published indicators of compromise.

### UniBLEed documents two root RCE chains on the Unitree G1, one of five bugs over Bluetooth

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://boschko.ca/g1-ble-rce/), [discussion](https://www.reddit.com/r/netsec/comments/1w05xwz/unibleed_unauthenticated_root_rce_on_any_unitree/)
- **Blurb:** A five-bug Bluetooth chain reached unauthenticated root on tested Unitree G1 units before Unitree patched the cloud key oracle.
- **Summary:** The write-up assigns CVE-2026-76639 to a chat_go path traversal and bashrunner whitelist chain that gave a standalone root shell over Ethernet or the robot's access point, and CVE-2026-76640 to a five-bug Bluetooth chain whose documented steps include a GATT characteristic registered with bare write permission, a Unitree cloud endpoint that returned any robot's AES-128 key to any free account without an ownership check, a heredoc injection in WiFi configuration, and a 1050-byte BSS overflow. The stated affected versions cover only the G1 builds the researcher directly tested, reproduced on four G1 units, with firmware V1.5.1.1 and V1.5.2 named in the timeline, and related Go2, B2, and R1 builds are not treated as proven vulnerable. The timeline records Unitree implementing an account-to-robot binding ownership check before returning the key between 2026-07-01 and 2026-08-06, and states Unitree now has patches, some internal at the time of posting, for the large majority if not all of the vulnerabilities.
- **Why it matters:** The chain's fleet-wide reach, including robot-to-robot spread within Bluetooth range, rested on a cloud endpoint serving per-device keys with no ownership check, which the timeline records Unitree gating during disclosure, and the author asks that the write-up be read as a point-in-time account of the platform during the research and disclosure period rather than a description of its current security posture.
- **Follow-up:** Track publication of CVE-2026-76639 and CVE-2026-76640, and whether Unitree states which firmware builds carry the fixes.

### SourceHut will prohibit LLM-assisted original content in its terms of service from 2026-09-10

- **Category:** Dev tools
- **Status:** confirmed
- **Sources:** [primary](https://sourcehut.org/blog/2026-08-27-tos-changes-and-llms/), [discussion](https://news.ycombinator.com/item?id=49461724)
- **Blurb:** SourceHut will prohibit LLM-assisted original content and AI-enabling software from 2026-09-10, with no retroactive enforcement.
- **Summary:** SourceHut announced terms of service changes effective 2026-09-10 that make LLM-assisted content, and software containing or enabling generative AI features, prohibited content, and it tells projects that intend to keep using generative AI to migrate off the platform. The policy targets original content, so mirrors of codebases such as the Linux kernel remain hostable, and SourceHut states that using LLMs privately to review work, ask questions, or perform security analysis before writing original code is aligned with the policy. SourceHut states there will be no retroactive enforcement for existing projects, that it will deploy no automated AI detection, and that violations are evaluated case by case with exceptions possible.
- **Why it matters:** A forge encoding a generative-AI position in its terms rather than a contribution guideline forces hosted projects to state a policy or move.
- **Follow-up:** Track enforcement and project migrations after 2026-09-10.

### Spectral Allocation accounts for Muon's advantage over Adam and proposes SAMuon

- **Category:** Paper
- **Status:** confirmed
- **Sources:** [primary](https://arxiv.org/abs/2608.25990)
- **Blurb:** A paper attributes Muon's edge over Adam to spectral allocation and proposes SAMuon, which cuts training tokens by up to 24 percent.
- **Summary:** The authors argue that spectral allocation accounts for Muon's advantage over Adam and introduce SAMuon. They report SAMuon reaching Muon's validation loss with 13.3 to 24.0 percent fewer training tokens across modded-nanogpt models from 124M to 1B parameters. They state SAMuon carries no persistent optimiser state and no notable extra FLOPs beyond Muon at scale.
- **Why it matters:** An optimiser with no persistent state and a reported token reduction at fixed loss changes the memory and cost profile of a pretraining run.

### A fuzzer-found divide by zero in FFmpeg's VPK demuxer crashes on a 21-byte input

- **Category:** Dev tools
- **Status:** confirmed
- **Sources:** [primary](https://code.ffmpeg.org/FFmpeg/FFmpeg/issues/24290), [discussion](https://news.ycombinator.com/item?id=49468642)
- **Blurb:** A 21-byte file that FFmpeg's probe reads as VPK triggers a divide by zero, crashing any app parsing untrusted media.
- **Summary:** A fuzzer-found divide by zero in FFmpeg's VPK demuxer crashes on a 21-byte input that the demuxer probe self-identifies as VPK. Any application calling avformat_open_input and av_read_frame on untrusted data is reachable. The issue locates the defect at `libavformat/vpk.c` line 89 and gives no affected-version scope, so which releases carry it is not yet known. A pull request to close the issue was opened on 2026-08-28.
- **Comments:** An FFmpeg member replied on the issue that it appears to be the same defect as a November 2024 ffmpeg-devel thread.
- **Why it matters:** Media parsing runs on untrusted input in most upload pipelines, and a 21-byte crash input needs no valid container to reach the demuxer.
- **Follow-up:** Track whether the pull request lands and whether the November 2024 report covers the same code path.

### Colin Percival ships Route 53 Files, an unofficial NFS filesystem over Route 53 records

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [primary](https://www.daemonology.net/blog/2026-08-27-Launching-Route-53-Files.html), [discussion](https://news.ycombinator.com/item?id=49465732)
- **Blurb:** Colin Percival released Route 53 Files, an unofficial NFS filesystem that stores files as Route 53 DNS records.
- **Summary:** The post is written in AWS launch style and its FAQ states this is not an AWS service. Records act as files and alias records act as symlinks. The post states a write through Route 53 Files takes about 90 seconds to reach live DNS, and an external Route 53 change takes up to six minutes to appear in the mount.
- **Why it matters:** The stated latency belongs to Route 53 Files and the S3 Files stack the post says it uses rather than to Route 53 itself, and the post cautions that reaching live DNS does not make a change visible worldwide because record TTLs and caching govern that.
