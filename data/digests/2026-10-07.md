### Attackers hijack three ccTLDs and obtain counterfeit TLS certificates for Google and other large services

- **Category:** Security
- **Status:** confirmed
- **Sources:** [report](https://arstechnica.com/security/2026/10/hackers-obtain-counterfeit-tls-certificates-for-google-and-other-large-services/), [discussion](https://news.ycombinator.com/item?id=49988230)
- **Blurb:** Google reports attackers hijacked the .gh, .sl and .as registries and passed domain validation to mint certificates for Google.
- **Summary:** Google reported on 2026-10-06 that attackers compromised the .gh, .sl and .as country code top-level domains, modified authoritative DNS records and nameserver delegations for selected domains, and passed automated domain control validation to obtain certificates for several Google domains and for other leading global brands and online services. No affected domain owner's own infrastructure was compromised and the certificate authorities followed all requirements, so the failure sits in the registry and validation path rather than in any one operator. Google updated Chrome to block the certificates it identified and had those for Google properties revoked, while stating it cannot guarantee it found every affected domain and that Chrome interventions do not protect non-Chrome users, and the disclosed scope stops there, because Google did not identify the affected domains it owns, named no other affected organization, and left both the number of unauthorized certificates issued and whether all non-Google certificates were blocked unstated.
- **Why it matters:** Automated domain control validation trusts whatever a registry's DNS returns, so one compromised ccTLD registry yields valid certificates for any domain under it without the domain owner being touched, the undisclosed scope means an affected owner cannot tell from the disclosure whether it was a target, and Google's advice as reported is to monitor certificate transparency logs for unexpected issuance and publish restrictive CAA records to stop reuse of cached validation data.
- **Follow-up:** The open items are registry-level remediation at the three ccTLDs and a response on cached validation reuse.

The fixed builds are 14.1-73.37 and 13.1-64.24 plus the FIPS and NDcPP equivalents, and appliances configured as a SAML service provider or identity provider also need the CVE-2026-88779 fixes, which CISA added on 2026-10-04. ### DNS root key-signing key rollover is scheduled for 2026-10-11

- **Category:** Infrastructure
- **Status:** confirmed
- **Sources:** [primary](https://blog.cloudflare.com/root-ksk-2024-rollover/), [IANA ceremony schedule](https://www.iana.org/dnssec/ceremonies), [discussion](https://news.ycombinator.com/item?id=49992038)
- **Blurb:** The DNS root switches signing from KSK-2017 to KSK-2024 on 2026-10-11, and resolvers missing the new anchor fail outright.
- **Summary:** On 2026-10-11 the DNS root switches the signer of its DNSKEY set from KSK-2017, key tag 20326, to KSK-2024, key tag 38696, which is only the second root KSK rollover ever, and both keys use RSA/SHA-256 so the key pair changes without an algorithm change. KSK-2024 has been published in the root DNSKEY set since 2025-01-11 so RFC 5011 automatic updates have had time to accept it, and Cloudflare reports that resolvers nonetheless lost learned anchor state during software upgrades and machine moves ahead of the 2018 rollover, which is why it added the key to its resolver's built-in anchors in July 2024 rather than relying on learning. Cloudflare has implemented the RFC 8509 trust anchor sentinel in 1.1.1.1, so a resolver can be asked directly whether it trusts key tag 38696 through is-ta-38696 and not-ta-38696 queries under a signed domain.
- **Why it matters:** A validating resolver that does not hold the new trust anchor can fail to resolve names under every top-level domain, and the failure mode is a working site that is unreachable rather than an error that points at DNS, so operators of self-run validating resolvers need to confirm the anchor is present and follow their vendor's trust-anchor update instructions, while users of Cloudflare DNS, 1.1.1.1 and Gateway DNS and most website operators need no action.
- **Follow-up:** The 2026-10-11 switch date rests on Cloudflare's post, and IANA's ceremony schedule corroborates only that KSK-2024 was generated on 2024-04-26 and imported on 2024-07-17 and that KSK-2017 is set for deletion at a ceremony on 2027-04-29, so watch for an IANA statement that makes the date primary and for resolver failure reports after the switch.

### OpenSSH 10.6 disables the LZ77 dictionary coder to mitigate a cross-channel plaintext recovery attack

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://www.openssh.org/releasenotes.html), [preprint](https://arxiv.org/abs/2609.07709), [discussion](https://news.ycombinator.com/item?id=49983791)
- **Blurb:** OpenSSH 10.6 disables the LZ77 dictionary coder to mitigate a cross-channel plaintext recovery attack on shared compression.
- **Summary:** OpenSSH 10.6 was released on 2026-10-06 with several security fixes, headlined by disabling the LZ77 dictionary coder to mitigate a chosen-plaintext attack that recovers secrets from one channel by interacting with the SSH session's shared compression dictionary through another channel, described in a preprint by Fabian Baeumer and Marcus Brinkmann. The release notes state the documentation already recommended against enabling Compression for sessions carrying both trusted and untrusted traffic, so the mitigated attack requires a non-default option, and the Compression option will be measurably less effective after the change, with application-level compression recommended instead. Other fixes restrict backslash and dollar characters in command-line usernames to block shell injection through ProxyCommand and Match exec, tighten sftp path validation against writes outside the target directory, and correct GSSAPI credential handling, and the notes state the team is shipping more frequently because security bugs found by AI tooling are being independently rediscovered by other researchers, which the maintainers read as evidence that non-reporting adversaries can find them too.
- **Why it matters:** Versions before 10.6 are affected, so the action is to take the update through distribution packages, and the compression attack additionally requires the non-default Compression option to have been enabled on a session carrying both trusted and untrusted traffic, while the username and sftp path fixes apply regardless of compression settings.

### matklad argues microbenchmarks should be tuned to about 300ms

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [primary](https://matklad.github.io/2026/10/05/benchmark-milliseconds.html), [discussion](https://news.ycombinator.com/item?id=49967427)
- **Blurb:** matklad argues microbenchmarks should be sized to about 300ms, long enough to drown fixed costs and short enough to rerun ten times.
- **Summary:** The rule is to adjust input size until a microbenchmark takes roughly 300ms. The reasoning is specific: milliseconds in the 1 to 999 range are integers that scan visually without unit switching, anything under about 10ms risks being dominated by fixed costs such as interpreter startup, hundreds of milliseconds is long enough to make one-off overheads irrelevant without more fragile correction techniques, and anything over a second makes running the benchmark ten times to eyeball variance too slow.
- **Why it matters:** The underlying claim is that benchmarking exists to give the author enough intuition to make a correct decision rather than to produce a precise performance measurement, which is directly applicable to anyone writing a benchmark harness.
