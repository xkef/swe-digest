### Cloudflare fixes a cross-tenant data exposure in Containers

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://blog.cloudflare.com/containers-cross-tenant-vulnerability/), [discussion](https://news.ycombinator.com/item?id=49831647)
- **Blurb:** Cloudflare fixed a Containers flaw that handed new tenants unzeroed 64 KiB disk blocks holding other customers' data.
- **Summary:** Cloudflare reports that a Workers Paid account could read residual disk blocks left behind by other customers' Containers, including directory structures, database pages, and structurally complete SQLite databases, because the dm-thin pool ran with `skip_block_zeroing` and handed reused 64 KiB blocks to a new tenant unzeroed. Cloudflare reviewed retained disk-I/O telemetry against detection signatures built from the proof of concept and attributed every match to the researchers and its own engineers, finding no other exploitation. Beyond the configuration change it retired all running container disks and cleared each host's cached dm-thin image snapshots fleet-wide, because zeroing new allocations does not sanitize mappings already present, and Cloudflare Sandboxes, which is built on Containers, was in scope. Cloudflare bounds the technique: it could not be aimed at a particular customer, workload, host or data, it could not reach an actively attached disk, and residual data was not guaranteed to be present in a reused block.
- **Why it matters:** Block reuse without zeroing breaks the isolation that every multi-tenant container platform sells, and the exposed material was complete enough to read as databases rather than as fragments.
- **Follow-up:** Track whether Cloudflare publishes the exposure window and any customer notification scope.

### File-notification APIs leak user and application behaviour on four operating systems

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://inoti.fyi/), [LWN](https://lwn.net/Articles/1096431/), [report](https://www.theregister.com/security/2026/09/24/decades-old-file-security-flaws-found-in-android-linux-macos-and-windows/5298672), [discussion](https://news.ycombinator.com/item?id=49835649)

## Security

### PHP stream wrapper sent Authorization and Cookie headers to the host a redirect pointed at

- **Category:** Security
- **Status:** confirmed
- **Sources:** [advisory](https://github.com/php/php-src/security/advisories/GHSA-fpwc-w8rq-cr92), [writeup](https://daubois.dev/blog/cve-2026-91766-php-http-redirect-credential-leak/), [discussion](https://news.ycombinator.com/item?id=49832673)
- **Blurb:** PHP patched a stream wrapper that forwarded Authorization and Cookie headers to whatever host a redirect pointed at.
- **Summary:** Any application that calls `file_get_contents()` or `fopen()` on an `http://` stream with a credential header and leaves `follow_location` at its default sent that header to whatever host, port or downgraded scheme the redirect pointed at. CVE-2026-91766 is rated moderate at CVSS 5.9, affects PHP below 8.2.34, 8.3.35, 8.4.26 and 8.5.11, and is patched in those four releases, published 2026-09-24. The advisory states the fix records scheme, host and port for the current request, strips `authorization`, `cookie` and `proxy-authorization` on a cross-origin hop, and keeps them withheld on every later hop.
- **Why it matters:** Secrets carried in a header of your own, such as `X-Api-Key`, are not stripped, so those callers still have to set `follow_location` to 0 and follow the redirect themselves.

### SourceHut build logs allowed account takeover through an ansi2html XSS

- **Category:** Security

- **Blurb:** An ansi2html XSS let anyone who could write to a SourceHut build log run script in every browser that viewed the job.

### macOS serial device nodes sit outside TCC, and Apple declined the report

- **Category:** Security
- **Status:** confirmed
- **Sources:** [primary](https://glyph.sh/posts/macos-cdc-acm-tcc-bypass/), [discussion](https://www.reddit.com/r/netsec/comments/1wplpp1/cdcacm_serial_interface_bypasses_tcc_on_macos/)

- **Why it matters:** Apple declined the report on 2026-05-20 as no identified security issue and left the 2026-05-21 rebuttal unanswered for four months, so this researcher-reported credential-theft path over USB has no vendor fix pending and no CVE assigned.

### Go 1.27 adds a portable SIMD package with emulation fallback

- **Category:** Languages
- **Status:** confirmed
- **Sources:** [primary](https://go.dev/blog/simd-experiment), [discussion](https://news.ycombinator.com/item?id=49843269)
- **Blurb:** Go 1.27 adds an experimental portable simd package that emulates missing operations where no hardware SIMD exists.
- **Summary:** The Go blog post of 2026-09-24 by David Chase and Junyang Shao describes an experimental platform-independent `simd` package in Go 1.27, loosely based on Highway for C++, alongside the architecture-dependent `archsimd` package that Go 1.26 introduced for amd64 and that 1.27 extends to arm64 NEON and wasm. The portable package removes fixed vector sizes from the type system, supports only the intersection of platform operations, and emulates the gaps, so code compiles and runs where there is no hardware SIMD at all. Both sit behind `GOEXPERIMENT=simd`, `GODEBUG=simd` accepts 0 for forced emulation and 128, 256 or 512 to pin vector width for testing with plus variants that panic only when an unsupported instruction is reached, and `ToArch` and `FromArch` let code drop to architecture-specific intrinsics for operations the portable set lacks.
- **Why it matters:** A vector API that still compiles and runs on targets without SIMD removes the per-architecture build split Go numeric code has needed, though reduction across a vector is absent in 1.27 and `ReduceSum` arrives in the next release.

## Engineering posts

### Kafgres reaches 700 MB/s produce throughput inside Postgres after replacing a tick loop with socket readiness

- **Category:** Engineering post
- **Status:** confirmed
- **Sources:** [primary](https://rynr.dev/blog/700mbskafgres/), [discussion](https://news.ycombinator.com/item?id=49840594)
- **Blurb:** Replacing a 5 ms tick loop with socket readiness took Kafgres produce throughput from 197 MB/s to 703 MB/s.
- **Summary:** The post is a profiling walkthrough of Kafgres, a Postgres extension that embeds a Kafka-protocol broker as a background worker and writes topic bytes straight to disk, and on-CPU profiling put 40.7% of time in parse, analyse and plan for metadata statements alone. Caching SPI plans with `SPI_keepplan`, relaxing the offset commit behind a `relaxed_produce_commit` GUC, and a few smaller changes took 256 KiB record throughput from 113.3 MB/s to 197.3 MB/s, and replacing the 5 ms tick loop with Postgres's own `WaitEventSet`, so the worker blocks until a client socket is readable rather than until the next timer edge, took it to 703.4 MB/s and 600k events per second on a roughly 0.25 dollar per hour Hetzner i9 box. Moving topic data to a second NVMe held the impact on pgbench against the same database under 1% at 100 MB/s, and the author notes the tradeoff Kafgres does not close: it fails over like the Postgres instance does and cannot absorb a zonal outage the way a three-zone Kafka cluster can.
- **Why it matters:** The numbers locate a background worker's cost in statement planning and timer latency rather than in disk, and both fixes are available to any Postgres extension that polls on a tick.
